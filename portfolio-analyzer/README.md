# Portfolio Analyzer

複数口座のポジションを1つにまとめ、資産配分・集中度・通貨・セクター・感応度・PERを確認する
ローカル専用ダッシュボードです。個人データを外部サービスへ送らず、自己完結した HTML を生成します。

## 現在できること

- 口座別・資産クラス別・通貨別の配分
- 口座損益、逆算元本、元本比損益率と照合メモ
- 現金比率、外貨比率、最大ポジション、実効ポジション数
- 口座で絞り込める保有明細、取得価額、現地通貨損益
- 3つの仮定シナリオによる評価額インパクト
- ETF・バランスファンドを内部構成へ展開したセクター・発行体分解
- HHIの逆数による実効ポジション数・実効セクター数
- 市場βを使う単一要因・複合ショック感応度と商品別の寄与
- 情勢連動シナリオ（A1〜A5）と、日付付き既知イベントの残日数・想定影響
- 過去5エピソードの実測ファクター変化を現在の保有に当てた再現
- 情報技術を装置／需要側プラットフォームに分けたファクターと、それを使ったシナリオ
- 方針上限を破る最小距離のショック組合せを逆算するリバース・ストレステスト
- 過去3年を現在の保有で再現した参考ES・最大DDと、26週ローリングの株債相関監視
- 商品をまたいで同じ材料に賭けている合計額（テーマ別集計）と、
  その内側をバリューチェーン上の位置で割った層別集計、
  さらに各社の開示セグメントまで割った事業別集計
- 実績・予想・提供会社基準に分離したPERと各カバー率
- 暫定投資方針の上限・下限チェック
- JSONの売買案を使った変更前後の配分・感応度・PER比較
- 確定値・推定値・残高調整の区別
- 数量×価格×為替、口座残高と明細合計の自動照合

> 価格・為替・分類は入力時点のスナップショットです。

## 分析の読み方

### 口座損益

口座損益が入力されている場合、`逆算元本 = 評価額 - 口座損益`、
`元本比損益率 = 口座損益 / 逆算元本` を表示します。算術的に一致していても、
商品別明細を確認していない場合は照合メモに残します。

### セクター分解

ETFとハッピーエイジング40は、運用会社の公式資料の構成比で内部の広義セクターへ展開します。
「セクター分類率」は、セクターとして展開した評価額のうち、個別の広義分類を付けられた割合です。
「実効セクター数」は総資産比で計算したHHIの逆数です。発行体分解は公表された上位構成銘柄だけを
別軸で集計し、セクター金額には加算しません。

### ファクター感応度

各行は他の条件を固定した線形近似です。シナリオ $s$ の評価額変化は次で計算します。

$$
\Delta V_s = \sum_i V_i \sum_f \beta_{i,f} s_f
$$

$V_i$ は商品の評価額、$\beta_{i,f}$ は商品 $i$ のファクター $f$ への感応度、$s_f$ は仮定した変化率です。
市場βは2023-08-15〜2026-08-14の3年週次収益率を基本とし、国内株は1306、米国ETFはSPYを
市場代理として `quantkit` のyfinanceフォールバックで推定しました。低相関商品のβは不安定です。
金利は修正デュレーションの一次近似で、`+100bp = +0.01`とします。

`株式全体` と `日本株` / `海外株` は同時投入を禁止し、IT・エネルギーは市場変動への追加ショック
として扱います。複合シナリオは単純加算なので、予測、VaR、最大損失ではありません。

#### 情報技術のバリューチェーン分解（`IT装置` / `IT需要側`）

`情報技術` はセクター全体の超過ショックですが、**同じセクターでも層によって景気感応度が
違います**。設備投資そのものが需要である製造装置は、AI 需要が伸び続けていても capex の
伸びが鈍った時点で落ちます。これを表現するため、2つの脚を `情報技術` の**内側に入れ子**で
持たせています。

| ファクター | 測定 | 意味 |
|---|---|---|
| `情報技術` | r(SMH) − r(SPY) | 市場に対するセクター超過 |
| `IT装置` | r(装置バスケット) − r(SMH) | セクターに対する装置の超過 |
| `IT需要側` | r(プラットフォームバスケット) − r(SMH) | セクターに対する需要側の超過 |

バスケットはいずれも**保有している発行体の等加重**です（装置＝アドバンテスト・東京
エレクトロン・ASML・AMAT・Lam・KLA、需要側＝Apple・Microsoft・Alphabet・Amazon・Meta）。
入れ子なので装置株は `株式全体 + 情報技術 + IT装置` を重ねて持ち、`情報技術` を
置き換えません。商品の `IT装置` 係数は `chain_role` で集計した発行体シェアから導出します。

この分け方の要点は、**`IT装置` を単独で叩けること**です。`情報技術` をゼロに置いたまま
`IT装置` だけを動かせば、「セクターは無事だが装置だけ落ちる」局面を表現できます。
1本のITファクターしかない場合、この局面の損失は構造上ゼロと評価されます。

#### 情勢連動シナリオ（A1〜A5）のパラメータ

以下のショック幅は**実測校正前の手置きの想定値**です。市況の定性的な観察から幅を決めており、
過去エピソードの実測やインプライド・ボラティリティからは導出していません。各値の根拠は
参照データの `assumption` に記載し、ダッシュボードの「感応度の前提」にも表示されます。

| ID | シナリオ | ショック | 置いた理由 |
|---|---|---|---|
| A1 | スタグフレーション型 | 株式全体 -10% / 日本金利 +75bp / 海外金利 +50bp / 不動産 -10% | 株債同時下落（相関の正転）の確認。日本国債ETFを増やす案の逆風テスト |
| A2 | 台湾サプライチェーン混乱 | 株式全体 -8% / IT超過 -25% / エネルギー +10% / 円高 5% | 先端プロセスの台湾集中。半導体保有が最も強く効く型 |
| A3 | 円高ショック大 | 外貨対円 -15% / 株式全体 -5% | 協調介入と日米金利差収斂。既存の円10%上昇より厳しい上限側 |
| A4 | AI決算失望 | IT超過 -15% / 株式全体 -3% | 半導体決算に連動するイベント型。`events` から日付を参照 |
| A5 | 原油供給ショック | エネルギー +20% / 日本金利 +50bp / 株式全体 -3% / IT超過 -5% | 原油→インフレ→長期金利の経路。エネルギー保有がヘッジに働く方向を確認 |

#### バリューチェーン・シナリオ（B1〜B3）

A系が「AI需要そのものが崩れる」型なのに対し、B系は**見立てが正しいまま負ける経路**と
その裏返しを置きます。`IT装置` を単独で動かせるようになって初めて書けるようになりました。

| ID | シナリオ | ショック | 置いた理由 |
|---|---|---|---|
| B1 | capex消化 | IT装置 -20% | 市場もセクターも動かず装置だけ調整する純粋形。実測の2024局面（IT装置 -7.80%）の2.5倍 |
| B2 | 効率化ショック | IT装置 -25% / IT需要側 +10% / IT超過 -5% | 需要は増えるがチップ集約度が下がる型。符号の組合せは実測5局面のうち4つと整合 |
| B3 | capex再加速 | IT装置 +25% / IT超過 +10% / 株式全体 +3% | 下方だけ並べると集中の対価が見えないため、上方も同じ枠組みで置く |

四半期ごと、または情勢が変わったときに幅を見直してください。シナリオを増やすと
`worst_compound_drawdown` が変わるため、**方針の閾値も併せて再確認**します。

#### 実測エピソード（`kind: "historical"`）

手置きのシナリオと並べて、過去の実際の局面を現在の保有・係数に当てた再現も表示します。
こちらはショック幅を**測定値**で埋めているため、`worst_compound_drawdown` とは分けて
`worst_historical_drawdown` に集計します。方針の閾値はどちらの指標にも設定できます。

推定は `scripts/estimate_factors.py` が担当します。ネットワークを使う手動ツールは
これと `scripts/reprice_snapshot.py` の2本だけで、結果を
`data/factor_estimates.json` に書き出します。ダッシュボードのビルドはこの
スナップショットだけを読み、オフラインのままです。

```bash
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/estimate_factors.py
```

このスクリプトが出すもの:

- 商品別の市場β（3年週次、国内は1306.T・米国はSPYを市場代理）
- ファクター共分散・相関・年率ボラティリティ
- 5つの過去エピソードにおけるファクター変化の実測値
- 除外したデータ欠陥の記録

価格の欠陥プリントは**前後11営業日の中央値から対数で0.4超離れた値**として除外し、
除外した日付と価格を `data_quality` に必ず残します。利回り系列は水準が正当に倍半分
動くため検査対象外です。加えて、調整済み終値の不連続が残す異常リターンを
MAD ベースの外れ値判定（z>8）で回帰から除き、除外日を `dropped_outliers` に記録します。

外れ値判定を掛けるのは**価格由来の7ファクターだけ**です。金利2本（`日本金利` /
`海外金利`）は対象外で、実際に適用したファクターは `outlier_screened_factors` に
記録します。

> この線引きは 2026-08-31 に実測した欠陥への修正です。判定はもともと「調整済み終値が
> 残す不連続」の検出器ですが、金利は財務省と `^TNX` の利回りの**差分**で、その種の欠陥を
> 持たないうえ散らばりが2桁小さい。日本金利の MAD スケールは 4.8bp なので z>8 は
> **週 39bp 超**を意味し、閾値が相場の普通の可動域に入り込んでいました。1本でも超えたら
> その週を全ファクターから落とす作りのため、2025-04-04 の週（10年 JGB 1.551% → 1.176%、
> 財務省の公表値で −37.5bp、z=8.09）が除外され、同じ週の `株式全体` −9.55%（3年窓で
> 最大の下げ、z=6.33 なので単独なら残る）が道連れになり、`株式全体` の年率ボラは
> 13.61% → 12.36% と**実態より安全側**に出ていました。

> 残る制約: 行単位の削除は維持しています。ファクター単位で落とすと共分散が pairwise
> deletion になり、半正定値性が壊れうるためです。また MAD の閾値は窓の端に敏感で、
> 上の週も窓を4日ずらすと z が8を下回ります。金利を対象から外したことでこの感応が
> 共分散へ波及する経路は塞がりましたが、価格側のファクターには残ります。

> 既知の制約: `株式全体` ファクターの実測系列は 0.5×1306.T + 0.5×SPY の等ウェイト
> ブレンドですが、個々のβは国内株なら1306.T、米国ETFならSPYという別々の代理に対して
> 推定しています。この不整合は共分散の解釈にのみ影響します。

### リバース・ストレステスト

「このショックなら何%下がるか」の逆で、**「方針上限まで下がるとしたら何が起きたときか」**を
逆算します。損失はファクターショックの一次結合 $L(s)=b^\top s$ なので、目標損失 $L^*$ を
固定してマハラノビス距離を最小化する問題

$$\min_s\; s^\top \Sigma^{-1} s \quad \text{s.t.}\quad b^\top s = -L^*$$

の解は逆行列を使わずに閉形式で求まります。

$$s^* = -L^* \frac{\Sigma b}{b^\top \Sigma b}, \qquad d = \frac{L^*}{\sqrt{b^\top \Sigma b}}$$

$b$ は各ファクター1単位あたりに動く評価額、$\Sigma$ は `data/factor_estimates.json` の
実測共分散です。乱数もシミュレーションも使わないため、同じ入力なら常に同じ答えになります。

$d$ は共分散の推定頻度（週次）を単位とする距離です。年率表記は $\sqrt{52}$ で割った値を
併記しますが、これは変動が独立同分布という仮定を置いた換算にすぎません。
**$d$ は確率ではありません。**正規性も相関の安定性も仮定していないので、
どの上限がどれだけ遠いかを比べる順位づけとして読みます。

対象になるのは `metric` が `worst_compound_drawdown` または `worst_historical_drawdown` で
`operator` が `<=` の方針上限です。`--no-factor-risk` を付けると計算を省きます。

### 参考テール指標とヘッジ監視

`data/factor_estimates.json` に保存した週次ファクター系列を**現在の保有**に当て直して、
擬似的な週次リターンを再構成します。実績のトラックレコードではなく再現です。

- **参考ES(97.5%)**: 下位2.5%（$\lceil n(1-\alpha)\rceil$ 本）の平均損失
- **参考最大DD**: 再現リターンを複利でつないだときの最大ドローダウン
- **株債相関**: 日本国債リターンと株式全体の26週ローリング相関。
  金利ファクターの符号を反転して求めます。**負なら債券が株安を和らげ、正なら株債同時安**

VaR ではなく ES を出しています。分布の仮定を置かず、観測された順序統計量だけを使います。

### テーマ別・バリューチェーン別の合算エクスポージャー

発行体ルックスルーには 2 つの集計軸を付けられます。どちらも `group: "issuer"` の
エクスポージャーでのみ読まれ、**互いに独立に集計されます**（片方だけ付けても構いません）。

| フィールド | 束ねるもの | 出力 |
|---|---|---|
| `theme` | 同じ材料で動く銘柄群 | テーマ別テーブル・`largest_theme_ratio` |
| `chain_role` | バリューチェーン上の位置 | チェーン別チャート/テーブル・`largest_chain_role_ratio` |

```json
{"group": "issuer", "category": "Nvidia", "weight": 0.2201,
 "theme": "AIサプライチェーン", "chain_role": "ロジック半導体"}
```

`theme` は「指数やETFに分散して持っていても、動く材料が同じなら1つの賭け」を可視化します。
`chain_role` はその内側を割り、**同じテーマでも層によって景気感応度が違う**ことを見ます。
設備投資を受け取る層（製造装置・半導体）と支払う層（需要側プラットフォーム）の
厚みが偏っていると、投資サイクルが反転したときに相殺が効きません。

軸を増やすときは `core.py` の `EXPOSURE_AXES` にフィールド名を足せば、
データセット `<軸>_exposure` と指標 `largest_<軸>_ratio` が自動で増えます。

### 事業別エクスポージャー（`business_mix`）

上の2軸は1発行体に1ラベルですが、`business_mix` だけは**1発行体を複数の事業に按分**します。
各社が開示しているセグメント売上構成をそのまま入れます。

```json
{"group": "issuer", "category": "Advantest", "weight": 1,
 "business_mix": {"SoCテスタ": 0.679958, "メモリテスタ": 0.151959,
                  "その他テストシステム": 0.071327, "テスタ関連サービス": 0.096756}}
```

シェアは合計1（±1%）でなければ検証エラーになります。一部だけ書くと発行体が黙って
縮んでしまうためです。出力は `business_line_exposure` と、
`largest_business_line_ratio` / `business_mix_coverage_ratio` の2指標。

読むときの前提が3つあります。

1. **売上構成であって価値構成ではありません。** 株価は将来利益の期待値なので、
   事業ごとに成長率と利益率が違えば市場が織り込む価値配分は売上比とずれます。
   このズレは開示からは測れないので、近似として読んでください
2. **セグメント定義は会社の都合で変わります。** アドバンテストは FY2026 Q1 に
   「半導体・部品テストシステム／メカトロニクス関連」から「テストシステム／サービス他」へ
   変更しました。時系列で追うときは切れ目に注意してください
3. **カバー率が100%未満なら全て下限値です。** `business_mix_coverage_ratio` は
   発行体を確認できている金額のうち内訳まで登録できている割合を示します

SEC の簡易API（companyfacts / companyconcept）は連結値しか返さず、セグメントは
次元付きXBRLなので簡単には取れません。銘柄数が限られるうちは決算資料からの手入力が
現実的です。

発行体を開示している部分だけの集計なので、**表示される比率は下限値**です
（カバー率は「発行体カバー率」カード、軸内の内訳は「確認済み発行体内シェア」列を
併読してください）。

### 既知イベント

参照データの `events` に日付付きのカタリストを登録すると、「今後の既知イベント」表に
基準日からの残日数と、`scenario_id` で紐づけたシナリオの想定影響が並びます。

```json
"events": [
  {"id": "nvda_earnings_2026q2", "date": "2026-08-26", "label": "NVIDIA 決算",
   "scenario_id": "compound_ai_earnings_miss", "note": "AI capexサイクルの主要確認点"}
]
```

`scenario_id` は登録済みシナリオのIDだけを受け付けます（未登録IDは読み込み時にエラー）。
残日数は参照データの `as_of` からの日数で、ビルド時刻には依存しません。
日銀会合・FOMC・ジャクソンホールなど日付を確認していないイベントは未登録です。

### PER

PERは実績、予想、提供会社基準を混ぜず、同じ区分内だけで評価額加重調和平均します。

$$
\mathrm{PER}_{portfolio} = \frac{\sum_i V_i}{\sum_i V_i / \mathrm{PER}_i}
$$

区分をまたぐ単一の「ポートフォリオPER」は表示しません。必ず「基準」「基準日」「鮮度」と
区分別カバー率を併読します。
債券、現金、REIT、PERを取得できないファンド部分は集計外です。

| `data/analysis_reference.private.json` | セクター・発行体、ファクター、PER、方針、出典 | `data/analysis_reference.example.json` |
| `data/rebalancing-proposal.private.json` | 売買数量と固定価格による比較案 | `data/rebalancing-proposal.example.json` |

各保有明細の `value_status` は次のいずれかです。

| 値 | 意味 |
|---|---|
| `exact` | 画面または正式な明細で評価額を確認済み |
| `estimated` | 数量・価格・口座合計などから推定 |
| `reconciliation` | 口座合計に合わせるための未分類差額 |

更新後はビルドを再実行します。別ファイルを使う場合:

```bash
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/build_dashboard.py \
  --input /path/to/portfolio.json \
  --reference /path/to/analysis-reference.json \
  --proposal /path/to/rebalancing-proposal.json
```

基本配分と簡易ストレスだけを生成する場合は `--no-analysis-reference` を付けます。

### 時価で洗い替える

`portfolio.private.json` は口座画面を転記した日の記録なので、日が経つと古くなります。
`scripts/reprice_snapshot.py` は**元ファイルを書き換えず**、数量を持つ明細の価格だけを
直近終値へ差し替えた別スナップショットを書き出します。

```bash
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/reprice_snapshot.py
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/build_dashboard.py \
  --input portfolio-analyzer/data/portfolio-<基準日>.private.json
```

読むときの前提が3つあります。

1. **洗い替えた明細は全て `estimated` になります。** 口座画面で確認した値ではなく
   終値×数量なので、定義どおりの区分です。「確定値比率」カードはこの分だけ落ちますが、
   評価額の精度が落ちたわけではありません
2. **時価の無いものは据え置きです。** 円現金（相場では動かないので `exact` のまま）、
   DC口座の残高、残高調整はいずれも元の日付の値のままで、理由は `source_note` に残ります
3. **市場ごとに基準日がずれます。** 日本株は当日終値でも、米国株は前営業日までしか
   取れません。銘柄ごとの実際の値付け日は `price_as_of` と `repricing.quotes` に入ります

口座損益は取得原価が未入力のため再計算できないので、洗い替えた口座では `null` に落とします
（古い損益額を残すと、新しい評価額と組み合わせて誤った逆算元本が出るため）。

```bash
  portfolio-analyzer/data/rebalancing-note.private.md
```
