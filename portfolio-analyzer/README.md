# Portfolio Analyzer

複数口座のポジションを1つにまとめ、資産配分・集中度・通貨・セクター・感応度・PERを確認する
ローカル専用ダッシュボードです。個人データを外部サービスへ送らず、自己完結した HTML を生成します。

## 現在できること

- 口座別・資産クラス別・通貨別の配分
- 口座損益、逆算元本、元本比損益率と照合メモ
- 現金比率、外貨比率、最大ポジション、実効ポジション数
- 口座で絞り込める保有明細、取得価額、現地通貨損益
- 3つの仮定シナリオによる評価額インパクト
- ETF・バランスファンドを内部構成へ展開したセクター・発行体分解
- HHIの逆数による実効ポジション数・実効セクター数
- 市場βを使う単一要因・複合ショック感応度と商品別の寄与
- 情勢連動シナリオ（A1〜A5）と、日付付き既知イベントの残日数・想定影響
- 過去5エピソードの実測ファクター変化を現在の保有に当てた再現
- 情報技術を装置／需要側プラットフォームに分けたファクターと、それを使ったシナリオ
- 方針上限を破る最小距離のショック組合せを逆算するリバース・ストレステスト
- 過去3年を現在の保有で再現した参考ES・最大DDと、26週ローリングの株債相関監視
- 商品をまたいで同じ材料に賭けている合計額（テーマ別集計）と、
  その内側をバリューチェーン上の位置で割った層別集計、
  さらに各社の開示セグメントまで割った事業別集計
- 実績・予想・提供会社基準に分離したPERと各カバー率
- 暫定投資方針の上限・下限チェック
- JSONの売買案を使った変更前後の配分・感応度・PER比較
- 証券会社の取引履歴から逆算した取得原価・実現損益・資金加重リターンと、
  円建て含み損益の価格要因／為替要因への分解
- 確定値・推定値・残高調整の区別
- 数量×価格×為替、口座残高と明細合計の自動照合

> 価格・為替・分類は入力時点のスナップショットです。

## 日次の損益ダッシュボード（mark-to-market）

`scripts/daily_pl_report.py` は、スナップショットの保有数量に yfinance の直近終値と USD/JPY を
掛けて評価し、IBKR の取引履歴を日次で再生して口座の NAV・損益の経路を復元した、自己完結の
HTML ダッシュボードを書きます。スナップショット・台帳・取引履歴は編集しません。

```bash
cd /home/kazumasa/projects
uv run --no-sync python portfolio-analyzer/scripts/daily_pl_report.py \
  --copy-to /mnt/c/Users/<user>/Documents/pl-daily   # 省略可
```

出力は `dist/pl-daily/pl-<基準日>.html` と `dist/pl-daily/latest.html`（既定はダーク配色、右上で切替）、
履歴は `data/mtm-history.private.jsonl`（1 日 1 行、同じ基準日は上書き）。構成は上から

- **ヘッドライン**: 総資産、日次損益、含み損益（原価既知分）、期間損益（全口座・入金控除後、既定 365 日）、
  開設来損益（実現・配当込み）、資金加重リターン（対象口座を併記）と期間内の最大ドローダウン
- **一般データ**: 口座別、資産配分、損益の内訳（含み／実現／配当／費用／為替換算／為替取引 ＝ NAV − 入金、
  下段に口座別の合計）
- **リスク**: 限度の状態、ルックスルー後のエクスポージャー（資産クラス・通貨・国・セクター）、ルックスルー上位銘柄、
  リスク量（ボラ・VaR・ES・ベータ、前日比）、リスク寄与、ストレス（シナリオと過去局面のリプレイ）— 定義は下の「リスク」
- 全保有の表（1D/1W/1M/1Y、1 年スパークライン、評価額、日次損益、平均取得、含み損益）
- **時系列**: 全口座の NAV と累計入金、損益（NAV − 累計入金）、日次損益、決済済み銘柄の実現損益、
  銘柄ごとの株価（▲買 ▼売、破線＝平均取得）と損益のカード

数字の定義:

- 日次損益 ＝ **全銘柄に共通の日付（どれか 1 つでも取引があった日）の直近 2 日**で比べた評価額の差（価格と為替の両方）。
  取引の無い日は前の終値のまま据え置くので、まだ開いていない市場（東京の夕方の米国株）や片方だけの祝日の銘柄は
  株の変化 0・FX だけになり、値動きは次に取引された日のレポートに 1 回だけ入ります（銘柄ごとの直近 2 終値を
  使っていた 2026-09-14 までは、閉まっている市場の前日の動きを繰り返し計上していた）。月曜は週末をまたぎます。
- 株 / FX の分解（ヘッドライン・口座別・保有ごと、値のみ）。株 ＋ FX ＝ 合計が厳密に成り立ちます。
  - 日次: 株 ＝ 数量 ×（終値 − 前日終値）× 当日レート、FX ＝ 日次損益 − 株（＝ 数量 × 前日終値 × レート変化）。
  - 含み: FX ＝ 取得原価（外貨）×（現在レート − 取得時平均レート）、株 ＝ 含み損益 − FX（手数料と交差項は株側）。
  - 円建ての保有は FX ＝ 0。
- USD 表記 ＝ 円の値 ÷ 基準日の USD/JPY 終値（全項目同じレートなので足し算が合う）。ヘッドライン・口座別・
  保有の円の値の直下に小さく併記。ドル建て銘柄の「ドルでの値動き」ではなく円の値の換算です。
- 税引後（見込み）＝ 今すべて売ったときの手取りの見込み。
  - 税率は、保有に `tax_rate` があればそれ、国内証券口座で NISA 枠だけで買った保有は 0%、それ以外は
    スナップショットの口座の `tax_rate`（海外証券口座・国内証券口座 20.315%、DC 口座 0%＝受取時の退職所得
    控除内とみなす）。NISA と特定の両方で買った保有は課税側の率にして注記に銘柄を出す。
  - 取引履歴の備考（`NISA成長投資枠` / `特定`）から、今持っている分を買った区分を判定。売り切った後の
    買い直しは新しい保有として判定し直す。
  - **損益通算**: 税率が 0 より大きい保有（上場株式等の課税口座分）は口座をまたいで 1 つにまとめる。
    NISA（0%）は通算に入らない。見込み税額 ＝ {max(含み損益計 ＋ 今年の実現損益 − 繰越損失, 0)
    − max(今年の実現損益 − 繰越損失, 0)} × 税率。今年の実現損益は両方の取引履歴から（国内は NISA 以外の
    売却だけ）、繰越損失はスナップショットの `tax.carryforward_loss_jpy`（既定 0）。
  - 見込み税額は含み益の銘柄に含み益の大きさで按分（還付になるときは含み損の銘柄に按分）するので、
    銘柄・口座・合計の税引後が足し算で合う。総資産（税引後）＝ 総資産 − 見込み税額。
  - 日次損益（税引後）＝ 日次損益 −（今日の按分税額 − 前日の按分税額）。前日は「含み損益 − 日次損益」で計算。
  - 配当との通算・外国税額控除・源泉徴収済みの税の精算は含まない。
  - 税率が決まらない保有が 1 つでもあれば、その合計の税引後は「—」。
- NAV・累計損益・期間損益・開設来損益・日次損益・損益の内訳は **3 口座の合計**（`timeseries.AccountSeries` を
  `combine`）。各口座の日次系列は
  - 海外証券口座: `data/ibkr-transactions.private.csv` を日次で再生（`timeseries.replay`）。履歴 CSV の最終日より
    後の取引は反映されないので、取引したら CSV を差し替えて `ingest_ibkr_transactions.py` も再実行してください。
  - 国内証券口座: 取引 CSV を日次で再生（`jpbroker.account_paths`）。現金は受渡金額の累積（入金 − 買い ＋ 売り ＋ 配当）、
    NAV ＝ 現金 ＋ Σ数量 × 終値、入金は `入金(振込)` の累積。手数料は取得原価に含むので「費用」は 0。
  - DC 口座: 口数 × 基準価額が NAV、拠出金累計が入金（`dcplan.account_paths`）。掛金履歴の最初の約定日
    （2025-08-26）より前は未定義で、合計もその日から。それ以前の掛金は拠出金累計に含まれている。
  - どの口座も各日で `NAV − 累計入金 ＝ 含み ＋ 実現 ＋ 配当 ＋ 費用 ＋ 為替換算 ＋ 為替取引` が成り立つ（テストで検証）。
  - 資金加重リターン（XIRR）は入金日付が分かる海外・国内の 2 口座（DC は履歴前の掛金日付が無い）。KPI に対象を併記。
  - 合計 NAV はスナップショットの総資産と、調整額（RECONCILIATION）と受渡前の現金の分だけずれます。
- 含み損益は取得原価が分かる保有だけ（海外証券口座＝台帳、国内証券口座＝`securities-transactions.private.csv`、
  DC 口座＝下記）。現金・調整額は据え置きです。
- DC 口座（ハッピーエイジング40）は運用会社の日次 CSV（`https://www.sompo-am.co.jp/fund/0885/data.csv`、
  1 万口あたりの基準価額）で評価します。数量は **万口**、平均取得も 1 万口あたり。
  - `data/dc-holding.private.json`: DC サイト「現在の資産状況」のある日の残高数量と拠出金累計（基準点）。
    原価は拠出金累計で、商品別の「購入金額」は使いません（過去のスイッチング益を含むため）。
  - `data/dc-transactions.private.tsv`: DC サイトの取引履歴をそのまま貼ったもの（タブ区切り、見出しの
    折り返しや繰り返しは読み飛ばす）。基準点より後の掛金で数量・原価を進め、前の掛金で過去へ戻します。
    **毎月の掛金が入ったら履歴を貼り足してください**（貼らないと数量が基準点のまま）。
  - CSV が取れない日は DC だけスナップショットの残高で据え置き、レポート全体は止めません。
  - 約定単価は約定日の翌営業日の基準価額と一致します（2025-08〜2026-08 の 13 件で確認）。

### リスク

日次レポートとメールの「リスク」は `src/portfolio_analyzer/risk.py` が当日の保有と 2 年分の終値から計算します。
元データは `--reference`（既定 `data/analysis_reference.private.json`）で、メインのダッシュボードと同じファイルです。

- **ルックスルー**: 商品ごとの `exposures`（セクター・発行体・資産）に評価額を掛けて集計。国は発行体の `country`、
  残りは商品の `country_default`（SMH/QQQ/XLE＝米国、国内 ETF・個別株＝日本）。通貨は建値通貨（`currency_mix` が
  あればそれ）。DC のバランス型は月次レポートの構成比から `asset_mix` / `currency_mix` / `country_mix` を手で入れた
  **推定**（外国株式を米 70／欧 20／他 10、外国債券を米 45／欧 40／他 15 で按分。`mix_note` に根拠）。
  発行体は商品横断で合算（アドバンテスト＝6857 直接 ＋ 1329・1475 経由）。現金は 現金／JPY／日本。
- **集中度**: 最大ポジション・上位 5・実効数（1/HHI。セクターは株式部分だけ）・最大セクター・ルックスルー後の
  最大銘柄・外貨比率・海外の最大単一国・現金比率。すべて総資産比。
- **リスク量**: 直近 252 営業日、**現在ウェイト固定**の日次円建て収益率（USD 建ては USD/JPY 込み）から、
  年率ボラ（√252）、過去シミュレーション VaR（1 日 95／99%、線形補間の分位点）、ES 97.5%（分位点以下の平均）、
  20 日 VaR は 1 日 95% の **√20 換算**、窓内の最悪日、ベータは単回帰（TOPIX＝1306.T 現地通貨、S&P 500＝SPY
  現地通貨、USD/JPY）。日付は全銘柄の和集合カレンダーで、閉まっている市場の日は収益率 0 として入るので
  相関・ベータは薄まる方向に出ます。
- **リスク寄与**: `RC_i = w_i (Σw)_i / wᵀΣw`（同じ窓の標本共分散、合計 1）。通貨・セクター・国へは各商品の
  ルックスルー比率で按分。比率と並べて「評価額の何倍のリスクを持っているか」を見る。
- **ストレス**: 参照ファイルの全シナリオを `Σ 評価額 × ファクター係数 × ショック` で換算（メインの
  ダッシュボードと同じ式。`kind: historical` は過去局面のファクター換算）。加えて `episodes` の 3 局面
  （2024-08 円キャリー巻き戻し、2024 AI capex 消化、2025-04 関税ショック）を**現在の保有に実際の価格変化を
  掛けて再現**（開始日直前の終値 → 終了日の終値、価格の無い保有は 0 でカバー率を表示）。価格履歴が届かない
  局面は出ません。ダウンロード開始日は最古の局面の 7 日前まで自動で遡ります。
- **限度**: `policy.limits` の 6 件（メインと共通）に加え、`policy.daily_limits` の暫定 3 件（外貨 ≤ 40%、
  海外の単一国 ≤ 30%、ルックスルー後の単一銘柄 ≤ 15%）。メインの読み込み（`core.py`）は計算できない指標の
  限度を拒否するので、日次だけの限度は別キーに置いています。超過は先頭に赤で出ます。
- **前日比**: 履歴（`mtm-history.private.jsonl`）の各行に `risk`（ボラ・VaR・ES・外貨比率・最大銘柄・最大セクター・
  ベータ 3 つ・超過数）を残し、前回レポートとの差を各指標に添えます。初回は差なし。
- **データの掃除**: yfinance には桁が 1 つずれた終値（1306.T の 2026-03-30/31、1475.T の 2024-08-08/09）があり、
  そのままだと TOPIX ベータが 0.00 になります。前後の水準から外れ、数日内に元の水準へ戻る値は欠測にして
  前値で埋め（`clean_closes`）、除外した日付を注記に出します。

### Windows で 1 日 2 回動かす

`scripts/windows/register_task.ps1` が、`run_daily_pl.cmd` を `%USERPROFILE%\Documents\pl-daily` に
コピーしてタスク スケジューラに 2 本登録します。

| タスク | いつ | 中身（件名の表記） |
|---|---|---|
| `PortfolioPLTokyo` | 月〜金 16:30 | 東京引け。日本株・DC は当日の終値、米国株はまだ前日終値なので USD/JPY の動きだけ（`--edition tokyo`、PC が止まっていたら飛ばす） |
| `PortfolioDailyPL` | 火〜土 07:30 | NY引け。前営業日を米国の終値まで含めて確定（`--edition ny`、PC が止まっていたら次の起動時） |

朝の回は前日夕方の回と同じ基準日で、履歴（`mtm-history.private.jsonl`）とレポートを上書きします。
日本だけの祝日の 16:30 は、日本株が動かず為替だけの回になります。

```powershell
powershell.exe -ExecutionPolicy Bypass -File \\wsl$\Ubuntu\home\kazumasa\projects\portfolio-analyzer\scripts\windows\register_task.ps1
```

cmd は `wsl.exe -d Ubuntu` 経由でこのリポジトリのスクリプトを呼び、HTML を
`Documents\pl-daily\latest.html`、ログを同じ場所の `run.log` に残します。時刻を変えるなら
`-EveningTime 17:00` / `-MorningTime 08:00` のように渡し、外すなら
`Unregister-ScheduledTask -TaskName PortfolioPLTokyo, PortfolioDailyPL`。

### メールで受け取る

`--email <宛先>`（複数指定可）で送ります。本文は HTML とプレーンテキストの両方で、HTML には
ダッシュボードと同じ項目が入ります: 主要銘柄の値動き・KPI 6 枚（総資産／日次／含み／期間／開設来／
資金加重リターンと最大DD）・口座別・資産配分・リスク（限度／通貨・国・セクターのエクスポージャー／
ルックスルー上位／リスク量／リスク寄与／ストレス。資産クラスは資産配分と重なるので省き、行数を絞った
コンパクト版）・損益の内訳（期間内と開設来、口座別）・保有・決済済み・
NAV と累計入金・累計損益・期間全体の日次損益・銘柄ごとのカード（数量／評価／比率／平均取得／
1W・1M・1Y／含み率、1 年の株価に平均取得の線と売買の帯、損益の推移）・注記。
テキスト版には「リスク: ボラ／VaR／ES／外貨／最大ルックスルー銘柄／超過数」の 1 行が入ります。
図を画像で付けたときの HTML 本体は約 98 KB（2026-09-15 実測）で、下記の折りたたみ境界の内側です。

図は**ダッシュボード自身の SVG を 1 枚ずつ PNG にして** `cid:` の inline 画像で置きます（`chartshot.render_pieces`）。
ダッシュボードを「メール用のレイアウト」（`dashboard.render(..., capture=True)`: 1 列、図は幅 540/520px の実寸）で
ヘッドレス Chromium に描かせ、ページが公開する各図の位置（`<body data-pieces>`）で 2 倍解像度のスクリーンショットを
切り出します。NAV・累計損益・日次損益・銘柄カードの株価と損益・保有表のスパークラインで計 36 枚、500 KB 前後。
HTML 本体は画像を含まないので小さく、Gmail の折りたたみにかかりにくくなります。

ブラウザが無いときや `--no-image` のときは、代わりに**テーブルのセルで描いた図**（`emailchart.py`）を
本文に入れます（階段状の線になります）。`--png` は時系列セクション全体を
`dist/pl-daily/pl-<基準日>.png` に書くだけのオプションです。

描き方は実測で決めています（送った本文を取り出して差分を取った結果）。

- **Gmail の Web/API から送ると `<img>` タグごと削られます。** `cid:` で参照しても Content-ID が
  `ii_...` に書き換わり、画像は添付に回ります。inline 画像を本文に出せるのは SMTP 直送（このスクリプト）
  だけです。

## 分析の読み方

### 口座損益

口座損益が入力されている場合、`逆算元本 = 評価額 - 口座損益`、
`元本比損益率 = 口座損益 / 逆算元本` を表示します。算術的に一致していても、
商品別明細を確認していない場合は照合メモに残します。

### セクター分解

ETFとハッピーエイジング40は、運用会社の公式資料の構成比で内部の広義セクターへ展開します。
「セクター分類率」は、セクターとして展開した評価額のうち、個別の広義分類を付けられた割合です。
「実効セクター数」は総資産比で計算したHHIの逆数です。発行体分解は公表された上位構成銘柄だけを
別軸で集計し、セクター金額には加算しません。

### ファクター感応度

各行は他の条件を固定した線形近似です。シナリオ $s$ の評価額変化は次で計算します。

$$
\Delta V_s = \sum_i V_i \sum_f \beta_{i,f} s_f
$$

$V_i$ は商品の評価額、$\beta_{i,f}$ は商品 $i$ のファクター $f$ への感応度、$s_f$ は仮定した変化率です。
市場βは2023-08-15〜2026-08-14の3年週次収益率を基本とし、国内株は1306、米国ETFはSPYを
市場代理として `quantkit` のyfinanceフォールバックで推定しました。低相関商品のβは不安定です。
金利は修正デュレーションの一次近似で、`+100bp = +0.01`とします。

`株式全体` と `日本株` / `海外株` は同時投入を禁止し、IT・エネルギーは市場変動への追加ショック
として扱います。複合シナリオは単純加算なので、予測、VaR、最大損失ではありません。

#### 情報技術のバリューチェーン分解（`IT装置` / `IT需要側`）

`情報技術` はセクター全体の超過ショックですが、**同じセクターでも層によって景気感応度が
違います**。設備投資そのものが需要である製造装置は、AI 需要が伸び続けていても capex の
伸びが鈍った時点で落ちます。これを表現するため、2つの脚を `情報技術` の**内側に入れ子**で
持たせています。

| ファクター | 測定 | 意味 |
|---|---|---|
| `情報技術` | r(SMH) − r(SPY) | 市場に対するセクター超過 |
| `IT装置` | r(装置バスケット) − r(SMH) | セクターに対する装置の超過 |
| `IT需要側` | r(プラットフォームバスケット) − r(SMH) | セクターに対する需要側の超過 |

バスケットはいずれも**保有している発行体の等加重**です（装置＝アドバンテスト・東京
エレクトロン・ASML・AMAT・Lam・KLA、需要側＝Apple・Microsoft・Alphabet・Amazon・Meta）。
入れ子なので装置株は `株式全体 + 情報技術 + IT装置` を重ねて持ち、`情報技術` を
置き換えません。商品の `IT装置` 係数は `chain_role` で集計した発行体シェアから導出します。

この分け方の要点は、**`IT装置` を単独で叩けること**です。`情報技術` をゼロに置いたまま
`IT装置` だけを動かせば、「セクターは無事だが装置だけ落ちる」局面を表現できます。
1本のITファクターしかない場合、この局面の損失は構造上ゼロと評価されます。

#### 情勢連動シナリオ（A1〜A5）のパラメータ

以下のショック幅は**実測校正前の手置きの想定値**です。市況の定性的な観察から幅を決めており、
過去エピソードの実測やインプライド・ボラティリティからは導出していません。各値の根拠は
参照データの `assumption` に記載し、ダッシュボードの「感応度の前提」にも表示されます。

| ID | シナリオ | ショック | 置いた理由 |
|---|---|---|---|
| A1 | スタグフレーション型 | 株式全体 -10% / 日本金利 +75bp / 海外金利 +50bp / 不動産 -10% | 株債同時下落（相関の正転）の確認。日本国債ETFを増やす案の逆風テスト |
| A2 | 台湾サプライチェーン混乱 | 株式全体 -8% / IT超過 -25% / エネルギー +10% / 円高 5% | 先端プロセスの台湾集中。半導体保有が最も強く効く型 |
| A3 | 円高ショック大 | 外貨対円 -15% / 株式全体 -5% | 協調介入と日米金利差収斂。既存の円10%上昇より厳しい上限側 |
| A4 | AI決算失望 | IT超過 -15% / 株式全体 -3% | 半導体決算に連動するイベント型。`events` から日付を参照 |
| A5 | 原油供給ショック | エネルギー +20% / 日本金利 +50bp / 株式全体 -3% / IT超過 -5% | 原油→インフレ→長期金利の経路。エネルギー保有がヘッジに働く方向を確認 |

#### バリューチェーン・シナリオ（B1〜B3）

A系が「AI需要そのものが崩れる」型なのに対し、B系は**見立てが正しいまま負ける経路**と
その裏返しを置きます。`IT装置` を単独で動かせるようになって初めて書けるようになりました。

| ID | シナリオ | ショック | 置いた理由 |
|---|---|---|---|
| B1 | capex消化 | IT装置 -20% | 市場もセクターも動かず装置だけ調整する純粋形。実測の2024局面（IT装置 -7.80%）の2.5倍 |
| B2 | 効率化ショック | IT装置 -25% / IT需要側 +10% / IT超過 -5% | 需要は増えるがチップ集約度が下がる型。符号の組合せは実測5局面のうち4つと整合 |
| B3 | capex再加速 | IT装置 +25% / IT超過 +10% / 株式全体 +3% | 下方だけ並べると集中の対価が見えないため、上方も同じ枠組みで置く |

四半期ごと、または情勢が変わったときに幅を見直してください。シナリオを増やすと
`worst_compound_drawdown` が変わるため、**方針の閾値も併せて再確認**します。

#### 実測エピソード（`kind: "historical"`）

手置きのシナリオと並べて、過去の実際の局面を現在の保有・係数に当てた再現も表示します。
こちらはショック幅を**測定値**で埋めているため、`worst_compound_drawdown` とは分けて
`worst_historical_drawdown` に集計します。方針の閾値はどちらの指標にも設定できます。

推定は `scripts/estimate_factors.py` が担当します。ネットワークを使う手動ツールは
これと `scripts/reprice_snapshot.py` の2本だけで、結果を
`data/factor_estimates.json` に書き出します。ダッシュボードのビルドはこの
スナップショットだけを読み、オフラインのままです。

```bash
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/estimate_factors.py
```

このスクリプトが出すもの:

- 商品別の市場β（3年週次、国内は1306.T・米国はSPYを市場代理）
- ファクター共分散・相関・年率ボラティリティ
- 5つの過去エピソードにおけるファクター変化の実測値
- 除外したデータ欠陥の記録

価格の欠陥プリントは**前後11営業日の中央値から対数で0.4超離れた値**として除外し、
除外した日付と価格を `data_quality` に必ず残します。利回り系列は水準が正当に倍半分
動くため検査対象外です。加えて、調整済み終値の不連続が残す異常リターンを
MAD ベースの外れ値判定（z>8）で回帰から除き、除外日を `dropped_outliers` に記録します。

外れ値判定を掛けるのは**価格由来の7ファクターだけ**です。金利2本（`日本金利` /
`海外金利`）は対象外で、実際に適用したファクターは `outlier_screened_factors` に
記録します。

> この線引きは 2026-08-31 に実測した欠陥への修正です。判定はもともと「調整済み終値が
> 残す不連続」の検出器ですが、金利は財務省と `^TNX` の利回りの**差分**で、その種の欠陥を
> 持たないうえ散らばりが2桁小さい。日本金利の MAD スケールは 4.8bp なので z>8 は
> **週 39bp 超**を意味し、閾値が相場の普通の可動域に入り込んでいました。1本でも超えたら
> その週を全ファクターから落とす作りのため、2025-04-04 の週（10年 JGB 1.551% → 1.176%、
> 財務省の公表値で −37.5bp、z=8.09）が除外され、同じ週の `株式全体` −9.55%（3年窓で
> 最大の下げ、z=6.33 なので単独なら残る）が道連れになり、`株式全体` の年率ボラは
> 13.61% → 12.36% と**実態より安全側**に出ていました。

> 残る制約: 行単位の削除は維持しています。ファクター単位で落とすと共分散が pairwise
> deletion になり、半正定値性が壊れうるためです。また MAD の閾値は窓の端に敏感で、
> 上の週も窓を4日ずらすと z が8を下回ります。金利を対象から外したことでこの感応が
> 共分散へ波及する経路は塞がりましたが、価格側のファクターには残ります。

> 既知の制約: `株式全体` ファクターの実測系列は 0.5×1306.T + 0.5×SPY の等ウェイト
> ブレンドですが、個々のβは国内株なら1306.T、米国ETFならSPYという別々の代理に対して
> 推定しています。この不整合は共分散の解釈にのみ影響します。

### リバース・ストレステスト

「このショックなら何%下がるか」の逆で、**「方針上限まで下がるとしたら何が起きたときか」**を
逆算します。損失はファクターショックの一次結合 $L(s)=b^\top s$ なので、目標損失 $L^*$ を
固定してマハラノビス距離を最小化する問題

$$\min_s\; s^\top \Sigma^{-1} s \quad \text{s.t.}\quad b^\top s = -L^*$$

の解は逆行列を使わずに閉形式で求まります。

$$s^* = -L^* \frac{\Sigma b}{b^\top \Sigma b}, \qquad d = \frac{L^*}{\sqrt{b^\top \Sigma b}}$$

$b$ は各ファクター1単位あたりに動く評価額、$\Sigma$ は `data/factor_estimates.json` の
実測共分散です。乱数もシミュレーションも使わないため、同じ入力なら常に同じ答えになります。

$d$ は共分散の推定頻度（週次）を単位とする距離です。年率表記は $\sqrt{52}$ で割った値を
併記しますが、これは変動が独立同分布という仮定を置いた換算にすぎません。
**$d$ は確率ではありません。**正規性も相関の安定性も仮定していないので、
どの上限がどれだけ遠いかを比べる順位づけとして読みます。

対象になるのは `metric` が `worst_compound_drawdown` または `worst_historical_drawdown` で
`operator` が `<=` の方針上限です。`--no-factor-risk` を付けると計算を省きます。

### 参考テール指標とヘッジ監視

`data/factor_estimates.json` に保存した週次ファクター系列を**現在の保有**に当て直して、
擬似的な週次リターンを再構成します。実績のトラックレコードではなく再現です。

- **参考ES(97.5%)**: 下位2.5%（$\lceil n(1-\alpha)\rceil$ 本）の平均損失
- **参考最大DD**: 再現リターンを複利でつないだときの最大ドローダウン
- **株債相関**: 日本国債リターンと株式全体の26週ローリング相関。
  金利ファクターの符号を反転して求めます。**負なら債券が株安を和らげ、正なら株債同時安**

VaR ではなく ES を出しています。分布の仮定を置かず、観測された順序統計量だけを使います。

### テーマ別・バリューチェーン別の合算エクスポージャー

発行体ルックスルーには 2 つの集計軸を付けられます。どちらも `group: "issuer"` の
エクスポージャーでのみ読まれ、**互いに独立に集計されます**（片方だけ付けても構いません）。

| フィールド | 束ねるもの | 出力 |
|---|---|---|
| `theme` | 同じ材料で動く銘柄群 | テーマ別テーブル・`largest_theme_ratio` |
| `chain_role` | バリューチェーン上の位置 | チェーン別チャート/テーブル・`largest_chain_role_ratio` |

```json
{"group": "issuer", "category": "Nvidia", "weight": 0.2201,
 "theme": "AIサプライチェーン", "chain_role": "ロジック半導体"}
```

`theme` は「指数やETFに分散して持っていても、動く材料が同じなら1つの賭け」を可視化します。
`chain_role` はその内側を割り、**同じテーマでも層によって景気感応度が違う**ことを見ます。
設備投資を受け取る層（製造装置・半導体）と支払う層（需要側プラットフォーム）の
厚みが偏っていると、投資サイクルが反転したときに相殺が効きません。

軸を増やすときは `core.py` の `EXPOSURE_AXES` にフィールド名を足せば、
データセット `<軸>_exposure` と指標 `largest_<軸>_ratio` が自動で増えます。

### 事業別エクスポージャー（`business_mix`）

上の2軸は1発行体に1ラベルですが、`business_mix` だけは**1発行体を複数の事業に按分**します。
各社が開示しているセグメント売上構成をそのまま入れます。

```json
{"group": "issuer", "category": "Advantest", "weight": 1,
 "business_mix": {"SoCテスタ": 0.679958, "メモリテスタ": 0.151959,
                  "その他テストシステム": 0.071327, "テスタ関連サービス": 0.096756}}
```

シェアは合計1（±1%）でなければ検証エラーになります。一部だけ書くと発行体が黙って
縮んでしまうためです。出力は `business_line_exposure` と、
`largest_business_line_ratio` / `business_mix_coverage_ratio` の2指標。

読むときの前提が3つあります。

1. **売上構成であって価値構成ではありません。** 株価は将来利益の期待値なので、
   事業ごとに成長率と利益率が違えば市場が織り込む価値配分は売上比とずれます。
   このズレは開示からは測れないので、近似として読んでください
2. **セグメント定義は会社の都合で変わります。** アドバンテストは FY2026 Q1 に
   「半導体・部品テストシステム／メカトロニクス関連」から「テストシステム／サービス他」へ
   変更しました。時系列で追うときは切れ目に注意してください
3. **カバー率が100%未満なら全て下限値です。** `business_mix_coverage_ratio` は
   発行体を確認できている金額のうち内訳まで登録できている割合を示します

SEC の簡易API（companyfacts / companyconcept）は連結値しか返さず、セグメントは
次元付きXBRLなので簡単には取れません。銘柄数が限られるうちは決算資料からの手入力が
現実的です。

発行体を開示している部分だけの集計なので、**表示される比率は下限値**です
（カバー率は「発行体カバー率」カード、軸内の内訳は「確認済み発行体内シェア」列を
併読してください）。

### 既知イベント

参照データの `events` に日付付きのカタリストを登録すると、「今後の既知イベント」表に
基準日からの残日数と、`scenario_id` で紐づけたシナリオの想定影響が並びます。

```json
"events": [
  {"id": "nvda_earnings_2026q2", "date": "2026-08-26", "label": "NVIDIA 決算",
   "scenario_id": "compound_ai_earnings_miss", "note": "AI capexサイクルの主要確認点"}
]
```

`scenario_id` は登録済みシナリオのIDだけを受け付けます（未登録IDは読み込み時にエラー）。
残日数は参照データの `as_of` からの日数で、ビルド時刻には依存しません。
日銀会合・FOMC・ジャクソンホールなど日付を確認していないイベントは未登録です。

### PER

PERは実績、予想、提供会社基準を混ぜず、同じ区分内だけで評価額加重調和平均します。

$$
\mathrm{PER}_{portfolio} = \frac{\sum_i V_i}{\sum_i V_i / \mathrm{PER}_i}
$$

区分をまたぐ単一の「ポートフォリオPER」は表示しません。必ず「基準」「基準日」「鮮度」と
区分別カバー率を併読します。
債券、現金、REIT、PERを取得できないファンド部分は集計外です。

| `estimated` | 数量・価格・口座合計などから推定 |
| `reconciliation` | 口座合計に合わせるための未分類差額 |

更新後はビルドを再実行します。別ファイルを使う場合:

```bash
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/build_dashboard.py \
  --input /path/to/portfolio.json \
  --reference /path/to/analysis-reference.json \
  --proposal /path/to/rebalancing-proposal.json
```

基本配分と簡易ストレスだけを生成する場合は `--no-analysis-reference` を付けます。

### 時価で洗い替える

`portfolio.private.json` は口座画面を転記した日の記録なので、日が経つと古くなります。
`scripts/reprice_snapshot.py` は**元ファイルを書き換えず**、数量を持つ明細の価格だけを
直近終値へ差し替えた別スナップショットを書き出します。

```bash
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/reprice_snapshot.py
uv run --package portfolio-analyzer python portfolio-analyzer/scripts/build_dashboard.py \
  --input portfolio-analyzer/data/portfolio-<基準日>.private.json
```

読むときの前提が3つあります。

1. **洗い替えた明細は全て `estimated` になります。** 口座画面で確認した値ではなく
   終値×数量なので、定義どおりの区分です。「確定値比率」カードはこの分だけ落ちますが、
   評価額の精度が落ちたわけではありません
2. **時価の無いものは据え置きです。** 円現金（相場では動かないので `exact` のまま）、
   DC口座の残高、残高調整はいずれも元の日付の値のままで、理由は `source_note` に残ります
3. **市場ごとに基準日がずれます。** 日本株は当日終値でも、米国株は前営業日までしか
   取れません。銘柄ごとの実際の値付け日は `price_as_of` と `repricing.quotes` に入ります

口座損益は取得原価が未入力のため再計算できないので、洗い替えた口座では `null` に落とします
（古い損益額を残すと、新しい評価額と組み合わせて誤った逆算元本が出るため）。

### 取引履歴から取得原価を逆算する

スナップショットは「今いくら持っているか」だけの記録なので、取得原価の欄が空のままでは
口座損益も元本比損益率も出せません。`scripts/ingest_ibkr_transactions.py` は証券会社の
取引履歴CSV（基準通貨建て）を平均法で再生し、取得原価と実績を埋めます。

```bash
uv run --package portfolio-analyzer python \
  portfolio-analyzer/scripts/ingest_ibkr_transactions.py \
  --snapshot portfolio-analyzer/data/portfolio-<基準日>.private.json

uv run --package portfolio-analyzer python \
  portfolio-analyzer/scripts/build_dashboard.py \
  --input portfolio-analyzer/data/portfolio-<基準日>-with-cost.private.json \
  --ledger portfolio-analyzer/data/ibkr-ledger.private.json
```

**書き戻す前に数量を突き合わせます。** 台帳から再生した建玉とスナップショットの数量が
1銘柄でも食い違えば、何も書かずに終了します。元スナップショットは書き換えず、
`-with-cost` を付けた別ファイルを出します。

#### 国内口座は証券会社のCSVをそのまま再生する

国内口座の保有にはスナップショット上の取得原価がなく、日次レポートの銘柄カードが
「原価なし」になっていました。`src/portfolio_analyzer/jpbroker.py` が証券会社の
取引履歴CSV（cp932・「商品分類,約定日,受渡日,銘柄,取引,…」）を読んで、`ibkr` と同じ形の
台帳を組み立てます。日次レポートは `--jp-transactions`（既定
`data/securities-transactions.private.csv`）があれば自動で読み、`--jp-account`（既定
`securities`）の口座に当てます。

この書式に固有の扱いが3つあります。

- **受渡金額には手数料が入っている。** 約定単価×数量が価格だけの原価で、差額が手数料です。
  `cost_basis_jpy` は実際に払った全額、`cost_basis_gross_jpy` が価格だけ、
  `commission_jpy` はその差（負値）。
- **株式分割は「保振増減資」行で来る。** 金額のない数量の増加なので、平均取得単価は
  割り下げます。
- **分割前の数量は今日の株数に直す。** Yahoo の `Close` は `auto_adjust=False` でも
  分割調整済みなので、分割前の建玉をそのままの株数で掛けると、分割の倍率ぶんの
  偽の損失が損益線に出ます。`replay()` は分割日より前の日付の数量に倍率を掛け、
  取引マーカーも数量×倍率・価格÷倍率に直します。

`mtm.mark_positions` は台帳を複数受け取れるので（口座ごとに1つ）、海外は IBKR の台帳、
国内はこの台帳、と並べて渡します。

#### 円建て損益は価格と為替が混ざる

外貨建て銘柄の円建て取得原価は約定日レートで換算されるため、円ベースの含み損益は
価格の動きと為替の動きの合成です。ダッシュボードはこれを分けて出します。

$$
\underbrace{q(P_1-P_0)S_0}_{\text{価格要因}}
+ \underbrace{qP_0(S_1-S_0)}_{\text{為替要因}}
+ \underbrace{q(P_1-P_0)(S_1-S_0)}_{\text{交差項}}
- \underbrace{f}_{\text{手数料}}
= qP_1S_1 - C
$$

$P_0$ と $S_0$ は平均取得単価と加重平均約定レート、$C$ は手数料込みの円建て取得原価です。
約定日レートは各約定行の `Gross Amount(JPY) / (Quantity × Price)` から復元します。

#### 台帳の読み方で注意すること

- **取得原価は平均法です。** 証券会社の税務上のロット計算（FIFO等）とは一致しないことが
  あります。全数売却した銘柄の実現損益は、どちらで数えても同じ金額です
- **`FX換算損益（外貨現金）` は保有証券の損益ではありません。** 外貨の現金残高を基準通貨へ
  評価替えした額で、銘柄別の為替要因とは別勘定です
- **資金加重リターン（XIRR）は市場のリターンではありません。** 入金日と現在評価額から
  求めた年率なので、入金のタイミングの巧拙が入ります
- 口座残高との照合差異を毎回表示します。1円を超えたら台帳のどれかのバケットが誤りです
