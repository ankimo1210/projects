# `labor_ai_quadrant` 包括レビュー（2026-08-17）

## 結論

このプロジェクトは、**業種別の探索的な「人手不足 × 生成AI exposure」マップとしては有用**で、
参照値を公表統計から再生成する経路もかなり丁寧に作られている。一方、現状の企業ランキングと
P/L換算を投資判断や利益予想に使うのは早い。最大の理由は次の3点である。

1. ILO の `mean_score_2025` はタスク別自動化ポテンシャルの平均スコアであり、
   **労働時間・人員・FTEの「代替可能割合」そのものではない**。これをそのまま割合として
   売上・利益へ掛ける段階で単位が変わっている。
2. 既定設定では1,642社すべてで `closable_gap = vacancy_rate` となり、P/Lの大きさは
   AI exposure や実現率ではなく、欠員率と推計限界利益率で決まる。さらに上位25社の
   **24社が親会社単体スコープ警告（※）**であり、順位は既知の会計スコープ歪みに支配されている。
3. 業種表と企業表で別々の中央値を使うため、同じ業種でも象限ラベルが一致しない。
   加えて、2026年8月17日時点の月中価格を「2026年8月末」と表示している。

用途別の判定は以下のとおり。

| 対象 | 判定 | 理由 |
|---|---|---|
| 33業種の相対的な探索マップ | **条件付きで利用可** | 公表統計へのトレーサビリティは良い。ただし Y軸は「代替割合」ではなく exposure index として読むべき |
| 企業の象限ラベル | **要修正** | 業種表と企業表の境界が異なり、6業種で意味が食い違う |
| 企業P/Lランキング | **現状は利用不可** | ILO指標の単位変換、売上回復仮定、親会社単体バイアスが順位を支配 |
| 株価バックテスト | **参考値に限定** | look-ahead・生存バイアスに加え、月中データを月末と表示し、キャッシュも更新されない |
| README / HTMLレポート | **公開前に再同期が必要** | 現行コード・データと異なる象限、式、件数、説明が残っている |

総合判定は **Needs revision**。マップの発想を捨てる必要はないが、Y軸の名称とP/Lへの橋渡しを
切り分け、企業ラベル・レポート・時点管理を一貫させる必要がある。

## 2. 良い点

以下は維持すべき設計である。

- 参照値とマッピング判断を [`tools/build_reference.py`](../tools/build_reference.py) に集約し、
  生成済みTOMLに出典と vintage を残している。
- X軸の生データ、標準化値、合成値、0–100の相対値を分離している。
- Y軸でも `ai_substitutable_share_pct` と相対化後の `ai_score` を別列にしており、
  相対スコアを直接P/Lへ掛けない防御がある。
- EDINETで単体と連結の context を厳密に分け、過年度・セグメント値の誤取得をテストしている。
- 0以下の営業利益、成立しない限界利益率、欠損値を巨大な正値やゼロに変換せず、NaNで落としている。
- 既知のマッピング弱点、丸め残差、look-ahead、生存バイアス、親会社単体問題を
  [`METHODOLOGY.md`](METHODOLOGY.md) と [`REVISION-2026-08-17.md`](REVISION-2026-08-17.md)
  にかなり率直に記録している。
- 保存済みデータでは重複コードがなく、主要財務列の欠損も約1–4%に収まっている。

この土台があるため、問題は「全体を作り直す」より、**指標の意味・境界・成果物契約を正す**ことで
改善できる。

### F-01 — ILOスコアは「労働割合」ではない（Critical）

現行処理は、ILOの各ISCO職業の `mean_score_2025` を100倍し、18職業区分で単純平均している
（[`build_reference.py:309-323`](../tools/build_reference.py#L309-L323)）。その後、業種の職業構成との
内積を `ai_substitutable_share_pct`、すなわち「AIで代替しうる労働の割合」と呼んでいる
（[`axes.py:63-85`](../src/labor_ai_quadrant/axes.py#L63-L85)）。P/Lではさらに、

```text
ai_freed_labor_pct = ai_substitutable_share_pct × realization_rate
```

としてFTE相当の余力へ変換している。

しかし、ILOの説明では、各タスクに0–1の**自動化ポテンシャルスコア**を付け、職業内タスクの
平均と標準偏差から exposure gradient を作っている。タスクの所要時間、業務上の中心性、
国内就業者数で重み付けされた「労働時間シェア」ではない。公式データでも、
`potential25 = Not Exposed` の231職業に `mean_score_2025 = 0.09–0.36` が存在する。
したがって0.31を31%へ変換しても、「31%の人員を空けられる」という意味にはならない。

ILO自身も、これは潜在的 exposure の上限であり、実際の影響ではないこと、また多くの仕事では
代替より変容が起こる可能性が高いと説明している。

- [ILO Working Paper 140](https://www.ilo.org/publications/generative-ai-and-jobs-refined-global-index-occupational-exposure)
- [ILO: How might generative AI impact different occupations?](https://www.ilo.org/resource/article/how-might-generative-ai-impact-different-occupations)
- [ILO著者が公開した職業・タスク別データ](https://github.com/pgmyrek/2025_GenAI_scores_ISCO08)

**影響:** 相対的な「exposureの高低」の順位には利用余地があるが、列名、単位、P/Lの絶対額、
「全33業種で欠員を埋められる」という結論は正当化されない。

**推奨:**

1. まず `ai_substitutable_share_pct` を `ai_exposure_index` のような無次元指数へ改名し、
   業種マップ専用にする。
2. P/Lは別モデルにし、少なくとも
   `対象タスクの労働時間比率 × 自動化可能率 × 導入率 × 業務実現率`
   を明示する。根拠がない項は低・中・高シナリオとして出す。
3. FTE換算の外部根拠ができるまでは「期待利益」ではなく「仮定上の容量上限」と表示する。

### F-02 — P/LランキングがAIではなく欠員率と親会社単体歪みに支配される（Critical）

既定値 `realization_rate = 0.30` で保存済みTOPIXデータを再計算すると、

- 1,642 / 1,642社で `closable_gap_pct == vacancy_rate_pct`
- `gap_coverage_x` は最小1.59倍、中央値4.44倍、最大34.17倍
- 実現率0.15では56社だけAI側が上限、0.30と0.50では0社

となった。この状態では、P/Lの式は実質的に

```text
op_margin_uplift_pp = vacancy_rate × contribution_margin
```

であり、**AI exposure の大きさも実現率も順位に効かない**。AI軸は相対象限への入場条件だけになる。

さらに、AI解放のrankable 288社のうち107社が `parent_employee_share < 0.20`。現行の
`op_margin_uplift_pp` 上位25社では24社がこの警告対象で、唯一の非警告も親会社従業員比率20.4%である。
上位業種も不動産10、小売9、卸売6に限定される。コードは問題を検知して `※` を付けているが、
**既知の壊れた値を主ランキングの24/25まで残す**と、注意書きでは補正できない。

`METHODOLOGY.md` はこの歪みを正しく認識している
（[`METHODOLOGY.md:414-426`](METHODOLOGY.md#L414-L426)）一方、レポート生成はそのまま順位へ採用する
（[`report.py:502-515`](../src/labor_ai_quadrant/report.py#L502-L515)）。

**推奨:**

- 主表を「スコープ確認済み」「スコープ不明」「親会社単体警告」の3表へ分ける。
- `※` を除外しただけの958社にはスコープ不明49社が含まれるため、確認済み
  `parent_employee_share >= 0.20` の909 rankable社と同一視しない。
- 連結P/Lに揃えられない企業は金額ランキングを出さず、業種exposureだけを表示する。
- saturation状態、実際にAI側がbindする社数、式の分解をレポート上部に常時表示する。

### F-03 — 業種表と企業表の象限定義が一致しない（High）

`sector_frame()` と `company_frame()` は、それぞれ自分の行集合で中央値を取り直す
（[`quadrant.py:18-54`](../src/labor_ai_quadrant/quadrant.py#L18-L54)）。J-Quants由来の1,642社は
全社 `labor_intensity = knowledge_tilt = mid` なので、企業値は業種値の反復である。それでも
銘柄数の多い業種が企業中央値を決めるため、業種表と企業表で6業種のラベルが食い違う。

特に、業種表のAI解放は5業種（不動産、サービス、卸売、情報・通信、小売）だが、企業中央値では
情報・通信業とサービス業が境界とほぼ同値になって下側へ落ちる。このためTOPIXの企業AI解放320社は
実質的に不動産・卸売・小売だけになり、業種マップの説明と企業ランキングの母集団が異なる。

また、企業1,642社の2×2表で右上は320社、周辺度数から独立を仮定した期待値は332.5社であり、
「右上は本質的に狭い」という企業レベルの主張は件数上ほぼ確認できない。33業種の連続スコアには
Pearson相関 -0.442（Spearman -0.474）があるため、主張は**業種レベルの記述**として限定すべきである。

**推奨:** 業種マップを正本にするなら、33業種から得た境界を企業にも固定適用する。
企業独自の中央値を使うなら別分析として明記し、レポートに企業側の境界も表示する。
同じ「AI解放」ラベルに異なる定義を使わない。

### F-04 — 欠員率から売上回復への変換が未検証（High）

現行説明は「欠員率が高い業種は、その分だけ本来より売上が低い」とし、
`recovered_revenue = revenue × closable_gap` と置く
（[`METHODOLOGY.md:332-374`](METHODOLOGY.md#L332-L374)）。しかし欠員率は未充足求人と常用労働者の比で、
実測された逸失売上率ではない。求人には離職補充、将来成長、恒常募集も含まれ、職種ごとの
売上寄与も同一ではない。

この式には暗黙に次の仮定が入っている。

- 労働投入に対する売上弾力性が1
- すべての欠員に即時に充足可能な需要がある
- AIで空いた時間を同じ売上活動へ100%再配置できる
- 品質低下、顧客への価格移転、AI導入費、学習期間がない
- 人件費は全額固定、その他費用は全額変動

文書は一部を限界として列挙しているが、数値列名は `expected_profit_gain` で、期待値を作る確率や
検証データはない。また `(営業利益 + 推計人件費) / 売上` は会計上の限界利益率ではなく、
全人件費を固定費とした**代理限界利益率**である。

**推奨:** `labor_output_elasticity`、`demand_capture_rate`、`pass_through_rate`、
`implementation_cost` を明示したシナリオ式にする。名称も `scenario_profit_gain`、
`proxy_incremental_margin` とし、点推定ではなくレンジで表示する。

### F-05 — バックテストの時点とキャッシュ更新が壊れている（High）

価格キャッシュ `_data/prices_monthly.json` は2026-08-17 19:00 JSTに生成され、1,636系列が
`2026-08` を持つ。コードはYahooの月次タイムスタンプを `%Y-%m` に丸めるため
（[`quadrant_performance.py:40-55`](../tools/quadrant_performance.py#L40-L55)）、月中の最新値も月末値と
区別できない。しかしREADMEと改定記録は「2026年8月末」と記載している。

| 時点 | AI解放 | ユニバース全体 | AI増益 |
|---|---:|---:|---:|
| 2026-07（完了月） | 182.94 | 207.95 | 234.75 |
| 2026-08（8/17時点の月中値） | 189.64 | 220.23 | 251.86 |

AI解放が全体を下回る方向は7月でも維持されるが、数値と日付ラベルは誤っている。

さらに `fetch_prices()` はキャッシュに**銘柄コードが存在するかだけ**を見ており、既存コードの系列を
再取得しない（[`quadrant_performance.py:66-79`](../tools/quadrant_performance.py#L66-L79)）。一度取得した
ティッカーは翌月以降も更新されず、再実行しても古い末尾のままになる。

バックテストには既に明記されたlook-ahead・生存バイアスに加え、月ごとの有効銘柄数が変わる、
配信異常を1点ではなく系列全体の除外で処理する、因子調整なしに「勝ったのは金利」と因果表現する、
という限界もある。

**推奨:** 最終完了月を既定にし、`as_of_timestamp` と月別coverageを保存する。キャッシュは
最終取得日から増分更新する。結果は「現行構成銘柄の記述統計」と呼び、金利・業種・size/value/betaを
統制するまでは因果表現を避ける。

### F-07 — 平均年間給与と1.25倍係数の説明が不正確（Medium）

[`company.py:196-219`](../src/labor_ai_quadrant/company.py#L196-L219) は「平均年間給与は現金給与のみ」とし、
1.25倍に社会保険料・賞与・退職給付を含める。しかし有価証券報告書では一般に、平均年間給与は
「賞与及び基準外賃金を含む」と注記される。例えば
[JR東日本の2026年有価証券報告書](https://www.jreast.co.jp/investor/securitiesreport/2026/pdf/securitiesreport.pdf)
も同じ定義である。

したがって係数に「賞与引当」を足す説明には二重計上の疑いがある。1.25自体が必ず誤りとは限らないが、
法定福利・退職給付・福利厚生の企業差を一律係数で扱うため、企業順位の限界利益率に系統誤差が入る。

**推奨:** 賞与込みの開示給与を起点とする説明へ直し、係数の構成を社会保険事業主負担、退職給付等に
分解する。企業横断の実績人件費率で校正し、少なくとも係数感応度をランキングに併記する。

### F-08 — 感応度分析が不確実性の大きい箇所を覆っていない（Medium）

現行interactiveレポートの感応度はX軸6指標のleave-one-outだけである。これは有用だが、より判断の
入るISCO↔日本職業分類、4桁ISCOの単純平均、規制ドラッグ、境界、親会社閾値、P/Lシナリオを振らない。

規制ドラッグを0にするだけで4業種が象限移動し、AI解放は5業種から7業種になる
（海運・空運がAI解放へ、機械・その他製品が低感応へ）。したがって「規制ドラッグは順位を
入れ替えない」という改定記録の表現は強すぎる。

また `threshold_method="fixed"` の50は、min-maxで作った相対スコア上の固定値であり、経済的な
絶対基準ではない。ユニバースが変われば同じ生値でも0–100値は変わる。

**推奨:** Y軸のマッピング・drag・境界を含むシナリオグリッドを出し、象限所属確率または
所属レンジを表示する。P/Lは低・中・高の幅で順位安定性を確認する。

### F-09 — 再現手順とテスト実行がそのままでは成立しない（Medium）

通常のプロジェクト向けコマンド

```bash
uv run --no-sync pytest labor_ai_quadrant/tests --noconftest -q
```

は6モジュールのcollectionで `ModuleNotFoundError: labor_ai_quadrant.axes` となった。
ルートの同名プロジェクトディレクトリがnamespace packageとして先に解決されるためで、
`--noconftest` だけでは直らない。パッケージを先にimportしてからpytestを起動すると110件は通った。

また `_data/` はgitignoreされ、生スナップショットを `build_reference.py` が自動取得するわけではない。
URLは記録されているが、ファイル名、取得日、checksum、取得・整形手順のmanifestがなく、別cloneで
同じ参照値を再生成できる保証が弱い。`rescore_topix.py` は比較元の
`_data/topix_scored.csv` を上書きするため、再現実験の入力と出力も分離されていない。

**推奨:**

- 通常の1コマンドで通るpytest設定へ修正し、そのコマンドをCIで使う。
- source manifest（URL、取得日、SHA-256、ライセンス、ファイル名）とdownload/verifyステップを追加する。
- `rescore_topix.py --input ... --output ...` とし、既定で入力を上書きしない。
- 参照再生成、象限境界一致、月末cutoff、両HTMLの主要文言、API認証失敗をテストする。

### F-10 — J-Quantsの認証失敗を空データとして扱いうる（Medium）

[`jquants.py:221-258`](../src/labor_ai_quadrant/providers/jquants.py#L221-L258) は日次スイープ中の
すべての `JQuantsError` を「単一日の失敗」としてcontinueする。403、無効キー、endpoint変更が
全日で発生しても、400日を走査した末に空DataFrameを返しうる。銘柄別取得も同様に各銘柄をskipする。
EDINET側には5日連続失敗で中断する防御があり、挙動が非対称である。

**推奨:** 400/404の「対象日が配信範囲外」と、401/403の認証・契約エラー、429、5xx、通信障害を
分類する。認証・schema・連続障害は即時または閾値で中断し、取得件数・対象日範囲・欠測率の
data contractを満たさなければ成果物を作らない。

### F-11 — 局所的な説明・単位不整合（Low–Medium）

- [`cli.py:242-243`](../src/labor_ai_quadrant/cli.py#L242-L243) は実現率を「実際に削減される割合」と説明するが、
  現行主経路は人員削減ではなく売上回復である。

- [`METHODOLOGY.md:277-280`](METHODOLOGY.md#L277-L280) は化学と医薬品の職業構成が同一と説明するが、

- `sector_labor_shortage.toml` の `overall_anchor.job_openings_ratio` と生成コードは1.12のままなのに、
  方法論本文は比較可能なアンカーを1.386へ訂正している。
- READMEは「analyst判断値は規制ドラッグだけ」とするが、ISCO対応、業種対応、重み、残差按分、

いずれも計算の主値を直ちに壊すものではないが、監査可能性と読み手の解釈を損なう。

### P0 — 外部共有・投資利用の前に必須

## 7. 修正後の受入基準

- 「%」で表示する列は、分子・分母・重み・単位を説明できる。ILO平均スコアをFTE%と呼ばない。
- 業種と企業で同じ象限名を使う場合、同じ境界を使い、全行で整合する。
- 既定レポートの主ランキングに親会社単体警告を混在させない。
- P/L表はシナリオ名、全パラメータ、saturation社数、対象スコープを表示する。
- バックテスト末尾は完了済み取引月で、正確なas-of、月別銘柄数、除外銘柄を保存する。
- READMEと両HTMLの主要件数・式・時点が自動テストで現行計算と一致する。
- 新規cloneでsource manifestから参照値を再生成でき、checksumが一致する。
- 文書に記載した標準pytestコマンドが回避策なしで通る。

この基準を満たせば、プロジェクトは「興味深い業種ヒューリスティック」から、
再現可能で誤読されにくい分析基盤へ進める。
