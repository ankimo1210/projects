## 2. 共通フィードバック：事実と仮説を分離する

初回評価から、次の論点が分かっています。

- 処理完了、自己作成テストの合格、リスク計算の内部整合性だけでは、良いカーブを推定したことにはなりません。
- 弱さの出る年限はモデルごとに異なります。全体平均だけでは短期・長期の問題を見落とします。
- 基準モデルを採用することも、高度モデルを採用することも、それだけでは成功・失敗を意味しません。
- 公開文書の支払規約と、ベンチマーク側の価格生成・評価の規約に不整合の疑いがあります。端数満期の支払日・元本償還日・クーポン計算の差が、推定カーブを歪める可能性があります。ただし、その寄与はまだ測定されていません。
- ゼロ金利の水準が近くても、傾きの違いによってフォワード誤差が増えることがあります。連続複利では `f(T) = z(T) + T z'(T)` です。
- 数値品質と提出形式は別の問題です。内容が存在しても、JSONキーや章構成が曖昧だと検証できません。一方、形式修正だけを数値精度の改善と呼んではいけません。

これらは診断の出発点であり、答えではありません。フィードバックの仮説に同意するための実験ではなく、**支持しない結果も残せる実験**をしてください。

### 支払規約についての重要な境界

実際の隠し真値を各モデルの価格付け関数に渡す検証は、実験主催者が別途行います。あなたは真値、生成器、採点器を見てはいけません。

あなたは公開仕様を基準に、独自に作った人工カーブと独立した価格計算で自己診断してください。公開仕様から一意に決まらない端数期間の扱いは、曖昧さを明記し、必要なら複数解釈を分けて比較してください。観測への適合が良いという理由だけで、ある規約が正しいと断定してはいけません。

明確な共通仕様の追補が提供されていない点は「未確定」と扱い、採用した暫定解釈を記録してください。ベンチマークの不整合を自分で修復・再生成することは禁止です。

## 3. 診断と改善の順序

### A. 変更前の再現と、検証計画の固定

まず `input/TASK.md` と `input/market_data/CONVENTIONS.md`、自分の初回コード・レポートを確認してください。

1. コピー上で初回CLIと全テストを実行し、挙動を再現する。環境差・再現できない点は記録する。
2. 実際のPython・ライブラリの版、乱数seed、入力ハッシュ、CLIコマンドを記録する。
3. 改善前後で比較する指標、検証分割、採用条件、主要仮説を `audit/protocol.md` に先に書く。
4. ソースを読んで確認した事実と、「誤差の原因かもしれない」という仮説を分ける。

途中で検証計画を変える必要が出たら、変更理由と時刻を追記し、それ以前の結果を消さないでください。初回の再現ができない場合は、比較の限界を明記し、改善率を捏造しないでください。

### B. カーブをフィットする前に、価格付けを検証

既知の割引関数 `D(T)` を直接受け取る診断用の価格付けインターフェースを用意してください。推定カーブの補間を通さず、価格付けだけを調べられる形にします。

少なくとも以下を確認してください。

- 預金の単利、OISのパーレート、債券のクーポン・価格と、出力ゼロ金利の連続複利を混同していないか。
- `%`、小数、bp、価格ポイント、額面100の換算が正しいか。
- 整数満期・端数満期で、支払日、経過期間、クーポン額、元本償還日が公開仕様と整合するか。
- 同じ `D(T)` を与えたとき、独立した価格式と一致するか。
- 金利が負でも、正の割引因子と有限の価格を保てるか。

平坦・右上がり／右下がり・曲率や山のある人工カーブなど、複数の独自ケースを使用してください。人工パラメータは自分で設定し、隠し市場の値を推測・復元しようとしてはいけません。

テスト対象と正解計算が同じ支払列関数・同じバグを共有する循環的なテストは避けてください。不一致があれば、商品属性・支払時点・支払額・価格差を保存し、規約解釈の違いと実装ミスを区別してください。

### C. 同じ価格付けの下で、基準モデルと高度モデルを比較

価格付けを変える実験と、曲線表現・平滑化・重み・検証分割を変える実験を、一度に混ぜないでください。

可能なら次の比較を残してください。

1. 変更前の再現。
2. 価格付けだけを変更した場合。変更不要なら、根拠を示して変更しない。
3. 価格付けを固定し、最も有力な設計要因を一つ変更した場合。
4. 検証で選んだ最終版。

人工データでは、同じ観測と同じ価格付け規約を使い、基準・高度モデルの**両方**を既知の人工カーブに照合してください。良いモデルを選べなかったのか、両方とも弱かったのかを区別します。

公開市場データには隠し真値がありません。公開クォートへの適合、ホールドアウト誤差、人工データでの真値誤差を混同しないでください。公開観測への過剰適合を成果にしないでください。

### D. 検証が弱点を隠していないか調べる

- 重複・近接年限の情報が学習と検証へ漏れない分割を使う。
- 短期 `T <= 2`、中期 `2 < T < 15`、長期 `T >= 15` と、商品別の結果を示す。対象数がゼロの区分はゼロ誤差ではなく欠測とする。
- 難しい年限、端点、不都合な商品群を、誤差を見てから検証対象から外さない。
- 単位補正・異常値検出などで学習する閾値や統計量は、原則として学習側から推定して検証側へ固定適用する。例外や残る漏洩リスクは明記する。
- 商品別の残差の単位、標準化の分母、重みを示す。異なる単位のRMSEをそのまま足さない。
- 残差が大きいだけで正当な年限構造を消していないか、逆に、異常クォートや古い観測を追いすぎていないか調べる。
- ゼロ金利・割引因子・フォワードの整合性を確認する。解析的導関数と離散差分は、節点・端点や粗い格子では違い得るため、格子を細かくした収束も確認する。
- 改善前後を同じ分割・同じ測定定義で比較する。検証設計の変更自体を試す場合は別実験にし、旧・新の両方の結果を残す。

検証分割は各モデルの研究判断を含みます。そのため、あなたの公開ホールドアウト指標を、そのまま他モデルとの共通尺度だと主張してはいけません。最終的なモデル間比較は主催者側の共通評価で行います。

### E. 証拠に基づいて採用する

高度モデルを必ず採用する必要はありません。初回より大きな変更をする必要もありません。

全体平均が改善しても特定年限・商品・ストレス条件が悪化した場合は、その悪化を隠さず、事前に決めた採用条件に照らして判断してください。複数変更を最終版に組み合わせた場合、一要因実験で確認できた効果と相互作用が未検証の部分を分けてください。

優先度は、価格付け・単位の正しさ、未見条件の精度、安定性・再現性です。テスト件数やレポートの長さを増やすこと自体を目標にしないでください。

## 4. モデル別の確認事項

以下は全モデルに同じ本文として提供するレビュー要約です。**自分の項目だけを個別の診断対象として扱ってください。** 他モデルの実装を読む許可でも、他モデルの手法を再現する指示でもありません。指摘は必ず自分のコードで確認してください。

### Astra

- 初回は短期より長期のゼロ金利誤差が目立った。
- `log1p(年限)` 上のゼロ金利スプラインについて、長期のノット配置、平滑化の単位・尺度、端点条件、ロバスト重みを一要因ずつ点検する。
- 過剰平滑化か過剰な振動かは、RMSEだけで決めつけない。ゼロ金利・フォワード・残差・年限別重みを確認する。
- 支払規約の影響を先に切り分ける。日本語レポートの形式修正と数値改善は別に記録する。

### Sol

- 初回は長期より短期のゼロ金利誤差が目立った。
- 商品単体を価格再現する平坦カーブの利回りを、満期時点のゼロ金利として使う近似を確認する。
- 半年バケットへの集約と、その後の中央値平滑化が、短期の年限情報を失っていないか調べる。補間法だけの交換ではなく、集約前の情報保持を検証する。
- 基準モデルが内部ホールドアウトで勝った理由を、短期・商品別・価格付け規約別に調べる。高度モデルへ強制的に切り替えるだけで改善すると仮定しない。

### Terra

- 初回は長期のカーブ誤差、単位異常・bid/ask反転の処理、提出サマリー・感度分析の形式が再確認点だった。
- log-DFスプラインの長期の曲率制御、平滑化強度の選択、端点条件と価格付け規約を切り分ける。
- 単位補正、反転修正、除外の実際の処理と監査ラベルが一致しているか確認する。ラベルだけを変更して成功扱いにしない。
- 短い実行時間や少ない出力を維持することより、優先度の高い数値弱点の検証を重視する。

### Luna

- 初回のゼロ金利精度は比較的良好だったが、フォワード形状と長期の精度には改善余地があった。
- 区分線形ゼロ金利の節点、曲率ペナルティ、フォワードの作り方を点検する。
- 「高度モデルのホールドアウト誤差が基準モデルより少し悪くても許容する」という選択条件が、最終目的に適切か検証する。許容幅を後付けで都合よく変えない。
- 既存の良い結果を壊さないことも採用条件に含める。モデル比較JSONとレポートの形式は数値性能と別に確認する。

### Sonnet

- 初回は短期ゼロ金利とフォワードの誤差が目立った。処理完了・テスト合格とは別の問題である。
- 基準モデルの区分線形ゼロ金利と解析的フォワードについて、節点・端点・格子上の差分との関係を確認する。
- 預金をすべて学習に残す設計、OISの検証候補を局所的な滑らかさで選別する設計が、難しい箇所の検証を欠いていないか調べる。
- 基準モデルが内部検証で勝ったことと、未知の真値に近いことは別である。高度モデルとの人工データ比較、商品別重み、中程度の異常値・鮮度の処理を点検する。

### Opus

- 初回の主データ精度は良好だったが、一部のストレス条件でフォワードの不安定さがあった。
- 自分で作る多様な人工カーブ・観測欠落・異常値・低流動性条件で、曲率制御、重み、モデル選択条件を検証する。特定の隠しケースを推測しない。
- テスト数や反復量を増やすだけではなく、悪化が出る条件を簡潔な再現例に落とす。
- 個人環境の固定絶対パスとモデル比較JSONを点検する。主データの良い精度を犠牲にした改善は明記する。

### Fable

- 初回の総合的な精度・頑健性は良好だったため、大規模な書き換えを前提にしない。
- 観測への適合から選んだ支払規約と公開仕様との整合性を、価格付け単体で確認する。
- ロバスト処理と年限依存ペナルティが、異なる人工形状・欠損・低流動性条件でも安定するか点検する。
- 感度分析JSONの構造を確認する。品質に実質的な改善が見られなければ、変更を限定して「確認できた改善なし」と報告してよい。

## 5. 成果物・互換性・改善記録

`submission/` は元の公開TASKにあるCLI・ディレクトリ構造・必須成果物をすべて満たしてください。CLIは任意の適合データに対して、既存出力なしで決定的に実行できなければなりません。

```bash
PYTHONPATH=src "$PYTHON_BIN" -m quantcurve.cli run \
  --market-data /absolute/path/to/market_observations.csv \
  --output-dir /absolute/path/to/output_directory \
  --valuation-date 2026-01-15
```

改善後サマリーは `submission/benchmark_summary.json` に新規作成し、初回のものと取り違えないでください。必須フィールドは公開TASKに従い、この改善ラウンドの実測値・範囲で埋めてください。

提出形式を全モデルで明確にします。

- `model_comparison.json` のトップレベルに `baseline`、`advanced`、`selected_model`、`selection_rationale` を持たせる。基準／高度の両方について、学習・ホールドアウトの指標と単位を記録する。
- `sensitivity.json` は少なくとも3つの名前付き実験をトップレベルキーとして持たせ、それぞれ条件・数値結果・解釈を格納する。形式のためだけの空キーを置かない。
- `benchmark_summary.json` の `failed_test_runs` など必須キーを落とさない。実測できないトークン・料金・割当消費量は `null` とし、推定や0で埋めない。
- HTMLは日本語でよいが、公開TASKの9章の役割を明確にする。章見出しに `Executive Summary`、`Methodology`、`Data Quality`、`Model Comparison`、`Sensitivity Analysis`、`Validation and Repricing`、`Charts`、`Limitations`、`Recommended Next Steps` を日本語と併記する。本文と図を伴わない見出しだけの対応は禁止。

`audit/` には以下を保存してください。

1. **protocol.md**：仮説、事前に決めた分割・指標・採用条件・時間制約、途中で変えた条件。
2. **experiments.csv**：実験ID、比較元、変更要因、入力/分割ID、モデル種別、測定対象、年限帯/商品、指標名、単位、変更前値、変更後値、実行時間、検証状態、採否。
3. **feedback_response.md**：各指摘に対するコード上の事実、実験、支持/棄却/未検証、残る不確実性。
4. **round_summary.json**：ラウンド名、モデルID・設定の確認状況、開始/終了UTC、追加作業秒数、制限時間、実験数、テスト結果、最終採用版、原本ハッシュ不変の成否、環境、seed、未検証事項、トークン・料金等の取得可否。
5. **logs/**：実行したコマンド、終了コード、必要な標準出力・エラー。失敗ログも保持する。

異なる尺度は分けて記録してください。

- 人工データの既知カーブに対するゼロ/フォワードRMSE（bp）。
- 公開観測・ホールドアウトの商品別価格/金利誤差と、定義を明示した正規化誤差。
- 内部整合性、テスト合否、規約差、提出形式。

誤差改善率を出す場合は `(変更前 − 変更後) / 変更前` と定義し、分母0・欠測・測定条件不一致では計算しないでください。主催者の隠しスコア、隠しRMSE、使用トークン、請求額を自分で捏造・復元してはいけません。

## 6. 終了前の検証と最終報告

時間上限内で、最終採用版に対して以下を実行してください。

- 全テストと、公開データからのフルCLIを新しい出力先で実行。
- 数値の有限性、単位、格子範囲、割引因子、フォワード、リスク、必須スキーマを確認。
- 図とHTMLを確認。実際に表示確認できなければ、その制約を明記。
- 最終変更後の検証が通らない場合は、検証済みの変更だけを採用する。未検証の実験を黙って最終版に混ぜない。
- 初回原本のハッシュ不変と、改善後プロジェクトの独立実行性を確認。

最終応答は簡潔に、次を含めてください。

1. 最終提出先。
2. 主な変更と採用理由。
3. **確認できた数値改善・悪化・改善なし**。測定対象を必ず区別する。
4. フィードバック仮説のうち、支持されたもの、棄却されたもの、未検証のもの。
5. 検証結果、追加作業時間、未解決の規約・精度・再現性リスク。

隠し採点を要求して反復することなく、この1ラウンドの提出を確定してください。改善しなかったという結果も、有効な実験結果です。
