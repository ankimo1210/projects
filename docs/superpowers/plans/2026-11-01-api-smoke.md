# API Smoke Test Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Compare structured JSON, a real Python tool round trip, and Japanese risk explanations through both providers' APIs.

**Architecture:** A small standalone Python runner uses one common fictional portfolio, schema, prompt, and arithmetic oracle. Each provider normally makes two generation requests with no automatic retry. A JSON record and Markdown table retain sanitized evidence under `_data/api-smoke/`.

**Tech Stack:** Python standard-library HTTP, existing jsonschema 4.26, unittest.

**Spec:** `api-smoke/README.md` and the user's requirements in this chat.

## Global Constraints

- No Web search, browser operations, Computer Use, balance checks, credential logging, or Git commits.
- No additional dependency installation; preserve all pre-existing and concurrent changes.
- Work only in the new `api-smoke/` directory and this plan; retain raw run data under `_data/api-smoke/`.
- Record actual API responses, request latency, input/output tokens, and PASS/FAIL. Do not estimate prices without verified official rates.
- Initial tool selection is automatic. Execute only the whitelisted Python function with the requested scenario.

## Review Focus

- Incorrect sign or basis-point units must fail the arithmetic oracle.
- Duplicate positions, booleans as amounts, wrong factors, and narrative contradictions must fail validation.
- A skipped tool, malformed arguments, truncation, or API error must not produce a false PASS.
- Both protocols must return the Python result with the matching call ID, without hidden retries.
- Credentials must not appear in request records, errors, generated files, or command-line arguments.
