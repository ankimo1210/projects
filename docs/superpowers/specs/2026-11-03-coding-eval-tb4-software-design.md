## 1. 目的と経緯

ユーザーの依頼（2026-11-02）: Artificial Analysis（以下 AA）の「Intelligence Index vs. Cost per Task」のような図を自分でも作れるようにしたい。モデルは OpenAI と Claude だけ、coding の能力が中心でよい。サブスクのプランを使う。ウェブサイトはいらない。

当初の動機は「手元で Opus を走らせて AA と同じ結果になるか試したい」。調べた結果（2026-11-02 時点）:

- AA の Intelligence Index v5.0（2026-10〜）の Coding カテゴリは FrontierCode 2.0（重み 15%）と Terminal-Bench 4.0（10%）。FrontierCode 2.0 は Cognition の非公開 132 課題で、手元では動かせない。Terminal-Bench 4.0（以下 TB4）は公開 66 課題。
- AA は TB4 の 66 課題をまとめた点数だけを公表しており、分野別・課題別の結果は出していない。
- TB4 の 66 課題は端末で完結する専門職の仕事で、ソフトウェアは 18 課題（他は科学 14、ML 11、業務 9、ハードウェア 5、セキュリティ 5、メディア 4）。

ユーザーはここで「ソフトウェアだけでテストしたい」と決めた。したがって本計画は **TB4 のソフトウェア 18 課題について、AA と同じ測り方でモデル・推論設定ごとの正解率と費用を自分で測り、AA 風の図を作る** ものである。AA の点数との一致判定は今回行わない（§15）。

本計画の実行器は、課題を Harbor の課題形式（TB4 と同じ）で受け取る作りにする。計画②の自作課題も同じ形式で書けば、同じ実行器・台帳・図に載る。

- 比べられない数字（AA の 66 課題の点数と本計画の 18 課題の点数など）を、比較できるかのように同じ図に並べること。

- **C2. 置き場所**: 新プロジェクト `/home/kazumasa/projects/coding-eval/`（uv workspace メンバー、README・`docs/STATUS.md` を持つ）。実行の生データは `/home/kazumasa/projects/_data/coding-eval/`（gitignore 済み）。リポジトリには設定・料金表・集計 CSV・図・検証の要約だけを入れる。
- **C3. 判定規則**: §9。
- **C4. 失敗と打ち切りの扱い**: §10。
- **C5. 費用の数え方**: §11。
- **C6. 拒否と fallback**: Opus の安全分類器による拒否は「モデル側の失敗」として数え、件数を別に出す（AA は拒否時に別モデルで答え直す server-side fallback を有効にしているが、サブスクでは同じことができないため）。`--fallback-model` は設定しない。応答のモデル ID が指定と違う呼び出しがあれば、その実行は無効にする。

- **C8. 混入検査の合格基準**: §8 の「混入検査の合格基準」。

- **C10. 枠切れ・時間帯切れの扱い**: 実行を捨てずに一時停止し、枠か時間帯が戻ったら同じ会話の続きから再開する（§12）。
- **C11. 夜間の時間帯**: 0:00〜8:00（日本時間）を既定とし、設定で変えられるようにする。
- **C12. 期間の相談ライン**: 配線確認の実費から見積もった本番の期間が 4 週間を超えるなら、本番の前にユーザーに相談する。

## 7. 実行の流れ

1. **準備**: WSL に Docker Engine を入れ（コマンドはユーザーが実行）、Harbor と mini-swe-agent を版固定で入れ、TB4 v4.0.0 を取得する。
2. **参照解答で採点を確認**: 18 課題の参照解答（oracle）を手元の Docker で複数回流し（TB4 の README は 5 回を推奨）、全課題が合格することを確かめる。モデルは使わないので枠は減らない。不合格・不安定な課題は除外候補としてユーザーに報告する。あわせて Docker イメージの容量を測る。
3. **混入の検査（プローブ）**: 条件ごとに短い固定入力を送り、モデルに届いた内容とツール一覧を記録する。§8 の合格基準を満たさない CLI のモデルは 1 回目から外し、理由をユーザーに報告する（ユーザー決定）。
4. **配線確認**: 条件ごとに 1〜2 課題を最後まで流し、台帳・採点・費用計算・枠の読み取り・一時停止と再開がつながっていることと、1 課題あたりの実費を確かめる。実費から本番の期間を見積もる（C12）。
5. **本番**: 18 課題 × 条件。夜間だけ回し、同時実行は CPU とメモリに収まる範囲（目安 2〜3）。週の上限・5 時間枠・時間帯で一時停止し、戻ったら再開する（§12）。
6. **集計と図**: §13。

## 8. AA の設定への合わせ方

AA の TB4 の設定（methodology ページ、2026-11-02 取得）:

- 66 課題を mini-swe-agent ハーネスで解かせ、pass@1 を 3 回の平均で出す。最大 500 ステップ、課題の制限時間は上流の定義どおり。
- mini-swe-agent の既定（interactive の mini 設定と指示文、native bash tool、文脈の要約なし）を使う。
- 推論モデルの温度は 0.6（ラボの推奨があればそれ）、最大出力トークンはラボが公表する最大値。
- Anthropic のモデルは server-side fallback を有効にしている（図の「with fallback」）。
- 数値はモデルの一次 API（Anthropic・OpenAI 自身の API）で測ったもの。

本計画で合わせるもの: mini-swe-agent の指示文（system・instance のテンプレート）、観測結果の書式、bash だけのツール、最大 500 ステップ、文脈の要約なし、課題と採点は TB4 のまま、制限時間 8 時間。

合わせられない、または未確認のもの（実装で確かめ、結果に注記する）: 温度（CLI から指定できない可能性）、最大出力トークン、fallback、CLI が足す要素の残り（ツール名の接頭辞など）、Codex の既定ツールのうち外せないもの、反復回数（本計画は 1 回、AA は 3 回）。

技術方針（細部は実装者に任せる。ただし下の検査は必須）:

- まず、AA が使ったと考えられる mini-swe-agent（Harbor 経由の場合はその統合）の版と、それが bash を「テキストで返す」方式か「ネイティブのツール呼び出し」方式かを確認する。AA は "native bash tool" と書いている。
- ネイティブのツール呼び出し方式なら、CLI 自身にエージェントのループを回させる案が有力。mini-swe-agent の指示文を system prompt に、instance テンプレートを最初のユーザー入力に置く。そのうえで、bash ツールを 1 つだけ持つローカルの MCP サーバ（課題コンテナの中でコマンドを実行し、mini-swe-agent の観測書式で返す）を渡す。
  - Claude Code の候補設定: `--system-prompt`、`--tools ""`、`--strict-mcp-config --mcp-config`、`--model`、`--effort`、`--output-format stream-json`、文脈の自動要約の無効化、500 ステップ上限。
  - Codex の候補設定: `model_instructions_file`、`--disable shell_tool`、MCP サーバの設定、`model_reasoning_effort`、`codex exec --json`。
- テキスト方式なら、mini-swe-agent のループをそのまま使い、モデル呼び出しだけを CLI（ツールなし）に置き換える案がある。
- **個人設定の隔離**: Claude Code は専用の設定ディレクトリと、公式の長期トークン（`claude setup-token` で発行し環境変数で渡すもの。存在と使い方は要確認）を使い、ユーザーの `~/.claude` を読ませない。`--bare` は OAuth を読まないのでサブスクでは使えない。Codex は認証情報だけを置いた専用の `CODEX_HOME` を使う。作業ディレクトリは空の一時ディレクトリにする。§7 の手順 3 のプローブで隔離を確認する。
- **Harbor との接続**: Harbor の独自エージェント（ホスト側で動き、課題コンテナの中でコマンドを実行するもの）として実装する案。Harbor の API と版は実装時に確認する。

混入検査の合格基準（C8）:

- 個人設定（CLAUDE.md、メモリ、hooks、plugins、skills、ユーザーの MCP、AGENTS.md）は一切届かないこと。
- 許す残りは、CLI が必ず付け足す固定の文だけ。Claude Code の自己紹介の 1 行（サブスク認証では必須とする第三者の報告がある。要確認）、MCP によるツール名の接頭辞（例 `mcp__…__bash`）、Codex の環境・権限の情報。どれも全課題で同じ内容であることを確かめ、全文を記録して結果に注記する。
- bash 以外に呼べるツールが残っていたら不合格。例えば Codex の `apply_patch` が残ると、編集が課題コンテナではなくホスト側の空のディレクトリに落ちる。
- 確かめ方は次の順に強い: CLI 自身のデバッグ記録（送ったリクエストを出せる場合）、短い固定入力での入力トークン数の照合、モデルにツール一覧を答えさせる（補助）。認証情報が経由する中継プロキシは使わない。
- 不合格なら、そのモデルは 1 回目から外す（ユーザー決定）。

## 9. 判定規則（C3、事前に固定）

- 主指標は、条件ごとの正解率（18 課題、各 1 回、pass@1）。課題は TB4 の採点で、テストが全部通れば合格。
- 正解率の 95% 区間を、課題単位のブートストラップで出す（課題数が少ないので、正確な二項区間も併記してよい）。
- 2 条件の比較は、同じ課題どうしの対応比較で行う。差の 95% 区間（課題単位の対応ブートストラップ）が 0 を含めば「判定できない」とし、含まなければ優劣ありとする。
- 18 課題 × 1 回では、10 ポイント程度より小さい差は判定できない見込み。このことを図と表に注記する。
- 揺れの測定（同じ条件での 2〜3 回の反復）は 1 回目の結果と枠を見て決める。反復した場合は、最良の回を選ばず全反復の平均を使う。

## 10. 失敗と打ち切り（C4）

規則は事前に決め、ログから機械的に分類する。

- 分母は、予定したすべての（課題, 条件, 反復）の組。
- **モデル側の原因 → 失敗として数え、費用も計上する**: ステップ上限・時間上限への到達、拒否、文脈長の超過、不正な出力、途中で諦めた場合。
- **基盤側の原因 → 無効**: リトライ上限を超えた CLI・サーバのエラー、一時停止から再開できなかった実行、Docker の異常、採点器のバグ。枠切れ・時間帯切れは無効にせず、一時停止する（§12）。無効な実行は途中から再開せず、最初からやり直す。K 回（実装者が決める）やり直しても無効なら、その課題を全条件から除外し、除外数を示す。無効な実行の費用は台帳に残し、条件の費用とは分けて示す。
- 原因を判別できないものは失敗とする。
- 上限はステップ数と時間だけで、全条件で共通にし、AA に合わせる（500 ステップ、8 時間）。時間は一時停止中を除いた実働時間で数える。1 課題あたりの費用上限は設けない（C9）。上限に達した割合は条件ごとに示す。
- 課題の最終状態と実行ログ（Harbor のジョブ出力）は保存し、採点器のバグが見つかったら全条件を採点し直せるようにする。

## 11. 費用の数え方（C5）

費用は「その実行を API で行っていたら払った額」の推計で、実際の支払いではない。請求データとの突き合わせはできない（サブスクのため）。

- **呼び出しごとに生データを残す**: 時刻、条件、課題、ステップ、セッション ID・リクエスト ID（取れるもの）、応答のモデル ID、停止理由、トークン数の区分（キャッシュなし入力、キャッシュ読み、キャッシュ書き（5 分と 1 時間を分ける）、出力、推論トークン）。推論トークンが出力に含まれる場合は二重に数えない。
- **料金表は版管理する**: 適用日、出典 URL、取得日を持つファイルにする。費用は「実行時の価格」と「現行価格での再計算」の 2 列。参考値として、Opus 5.5 は 100 万トークンあたり入力 $4・出力 $20、キャッシュ読みは入力の 5%（2026-11-02、AA と私のメモ。実装時に公式ページで確認）。
- 1 課題あたりの費用は、その実行の全呼び出しの合計。条件ごとに平均と中央値を出し、区間も付ける。
- usage が欠けた呼び出しは 0 円で埋めない。欠けた割合を点ごとに示し、5% を超えた点は白抜きにする（閾値は私の判断）。
- 費用はサブスクの CLI が実際に行ったキャッシュの使い方（Claude Code は 1 時間キャッシュに書く）をそのまま反映する。AA はキャッシュ率に別の仮定を使っているので、費用の絶対値は AA と一致しない前提で扱う。
- 一時停止からの再開でキャッシュが切れて余分に書き込んだ分は、台帳に別の区分で記録し、図と表の費用には含めない（AA の実行には一時停止がないため）。枠の消費としては数える。

## 12. 枠の管理

- **週の上限**: この計測で増えた週の使用率が、Claude・ChatGPT とも 25 ポイント（週の枠の 25%）に達したら止め、残りは翌週の枠で回す（ユーザー決定）。増加分は、計測が動いている間の使用率の変化で数える。
- **時間帯**: 夜間（既定 0:00〜8:00 日本時間、C11）だけ回す（ユーザー決定）。時間帯の外では実行中の課題を一時停止し、コンテナは残す。
- **5 時間枠**: 尽きたら一時停止し、戻ったら再開する。
- **一時停止と再開**: モデルを次に呼ぶ前で止め、同じ会話の続きから再開する（Claude Code は `--resume`、Codex は `codex exec resume` を想定。要確認）。止まっていた時間は 8 時間の制限に数えない（Harbor 側の制限時間は十分長くし、実働 8 時間は自前で数える）。
- **読み取り**: Claude は `claude -p` の stream-json に出る `rate_limit_event`（`five_hour`・`seven_day` の使用率）を読む。Codex は `codex exec --json` が出す枠の情報を読む（形式は要確認）。Codex で読めない場合は、配線確認の実費から決めた週あたりの実行数の上限で代用する。
- **期間の見込み**: Claude の週 25% は API 換算で週 $70〜110 にあたる。Opus high の 18 課題（$50〜700、未実測）は 1〜数週間かかりうる。配線確認の実費で見直す（C12）。
- 実行はユーザーの開始指示で始める。

## 13. 出力

- **図（PNG）**: AA の図に倣う。
  - 縦軸は正解率（0〜100%）、横軸は 1 課題あたりの API 換算費用（USD、対数目盛）。
  - 1 点が 1 条件で、ラベルは「モデル（推論設定）」、色は会社別（AA に倣い OpenAI は黒、Anthropic は橙）。
  - 縦横に誤差の幅を付け、観測されたパレート線を点線で引く。
  - 注記に、課題数、反復数、AA の設定との違い、データ取得日、TB4 の版を入れる。
- **表（CSV と Markdown）**:
  - 条件ごとの表: 正解率と区間、費用（平均・中央値）、平均時間、拒否数、無効数、上限到達率、usage の欠測率。
  - 課題 × 条件の合否表。
- 図と表は、保存した結果ファイルだけから再生成できるようにする。
