# 写真アーカイブの F: 集約設計

- 作成日: 2026-10-12（日本時間）
- 状態: 計画作成済み・実装および実データ移行は未着手
- 対象: Windows の写真保存処理、通常の写真・動画コピー、iCloud の受け取りデータ
- 実装手順: [移行計画](../plans/2026-10-12-photo-archive-migration.md)
- 正本: この設計と実装計画。実機のパス・識別子・写真台帳はローカルの私有記録。

## 1. 目的と成功条件

普段の撮影・閲覧・同期には iPhone / iCloud を使い、PC 上の原本保管と整理を F: の通常フォルダーへ集約する。C: は iCloud の受け取りと検証中の一時保存に使う。

成功条件は以下の三つに分ける。

1. **保管先の移行完了**: 宣言した入力集合のすべてのファイルが、F: で新規保存済み、内容と関係情報まで一致する既存保存へ対応済み、または元の場所で保護継続、のいずれかに分類される。未検証を保存済みと数えない。
2. **日次運用の切替完了**: 既存の毎日20時のタスクが新しい保存先で動き、増分・再実行・USB切断・クラウド取得失敗を正しく扱う。手動2回と定時1回の実績を確認する。
3. **容量解放完了**: 検証済みの削除候補だけを個別に処理し、実際の空き容量を測る。独立したコピーが証明できない分は C: に残し、その量を未解放として報告する。

Windows が表示しているファイル集合と、iCloud 全体の資産集合は同一だと仮定しない。全 iCloud 原本・Live Photos・編集情報の完全保存を称するには、別途取得経路と件数・構成要素の検証が必要である。通常フォルダーだけで Apple のアルバム、人物認識、非破壊編集履歴を完全再現するとは約束しない。

## 3. 入力と除外範囲

実機の絶対パスは `environment.private.json` に記録する。公開リポジトリにはユーザー名、写真のファイル名、撮影場所、アカウント識別子、台帳、ログ、実際のハッシュ一覧を書かない。

| 別名 | 取扱い |
|---|---|
| `OLD_C` / `OLD_F` | 読取台帳を作り、通常ファイルを新しい保存先へコピーする。初回は既存F側もコピーし、元を残す |
| `ICLOUD` | 登録済み同期ルートだけを読取。必要なファイルだけダウンロードし、通常ファイルとしてFへ保存 |
| `MAC_LEGACY` | 場所と保護範囲を記録し、パッケージ全体を保持。今回の統合・内部削除・改名対象外 |
| `SECOND_COPY` | F以外の媒体、または取得し直して照合済みのクラウド原本。なければ該当Cファイルを保持 |

端末バックアップ、LINE、健康・口座データ、他プロジェクト、同期設定の停止、アカウント変更、ドライブの再フォーマットは対象外。共有アルバム・隠し写真・他アカウントは、入力集合への登録と完全性を確認できた場合だけ追加する。

## 4. 保存形式と関連ファイル

新設予定の保存先を以下に固定する。実機で未作成であることは確認済み。作成前に媒体識別と境界検査を行う。

```text
F:\PhotoArchive\
  archive-marker.json
  media\YYYY\MM\<安全な元名>__<bundle-id先頭12文字>\<元ファイル名>
  media\_undated\<安全な元名>__<bundle-id先頭12文字>\<元ファイル名>
  catalog\
  receipts\
  staging\<run-id>\
  retained\<batch-id>\
```

- `archive-marker.json` に schema_version、archive_id、媒体識別との対応を記録する。
- 公開コード・テストは `docs/knowledge/photo-archive/` に新設予定。実行時は Windows ローカルの管理フォルダーへ検証済みリリースを配置する。
- ファイル名を変えても写真の内容と来歴を追えるよう、完成後の整理は台帳の対応も更新する。編集は原本への上書きではなく新しい版として保存する。移行時点では写真閲覧ソフトやクラウド側のアルバム構成を変更しない。
- 撮影年月はメタデータから決める。日時にオフセットがある場合はその値を保持し、UTCと生の撮影日時を併記する。オフセット不明の写真は記録された撮影日の年月を使い、JSTを推測で付けない。
- 動画の時刻規則はコンテナと撮影機器の検証で確定する。Live Photo は画像側の撮影年月にそろえる。
- 撮影日時が分からない、矛盾する、範囲が不自然、またはメタデータ読取が失敗した場合は `_undated` に保存し、元の時刻・理由を残す。ファイルのコピー日時を撮影日時に置換しない。
- Live Photo は画像と動画の ContentIdentifier を優先して対応させる。ファイル名だけで同一写真と判定しない。識別子の不足、複数対応、片方不足は保留として記録する。
- AAE、XMP、AppleDouble、RAWと対応画像、編集後の画像等を構成要素として保存する。AAEの関連付けが証明できなければ、原本と元ディレクトリーの文脈を保った保留束にする。
- バイトが同じ画像でも、対応動画や編集ファイルが異なる場合は同じ完成資産に統合しない。
- `bundle-id` はスキーマ版、構成要素の役割、各SHA-256、検証済みの関連、編集バージョンの正規化JSONから計算する。元名と元位置は別名台帳に保持し、名前の違いだけでは内容の識別子を変えない。関連未確認の束は元ディレクトリーの文脈も識別に含め、異なる入力を安易に統合しない。内部の完全ハッシュで衝突を判定し、短縮表記だけを同一性に使わない。
- 元名・元位置の別名を台帳に保持する。異なる名前の同一完成束は一つの保存実体に対応できる。ファイルシステム上のケース差や Unicode 正規化による衝突も、復元可能な別名として残す。
- 不明な再解析ポイント・EFS・未保全の代替ストリームは保留。リンクをたどって入力範囲外を読まない。exFATのためNTFSのACL等をそのまま移す移行ではない。別ストリームを保全できない元ファイルは削除候補にしない。
- 元ファイル内のEXIF・GPS・編集情報は書き換えない。公開ログには出さず、元のバイト列として保管する。

ExifTool をメタデータの読取だけに使用する。公式Windows版の安定版、13.53以上を条件とし、実行前に具体的な版・取得URL・配布物と実行ファイルのSHA-256を私有記録に固定する。タグ書込、画像再圧縮、自動更新は使わない。配布物を検証できなければ、その工程を止める。

## 5. 台帳・証跡・状態

私有記録のスキーマを以下に固定する。

- **FileRecord**: source_alias、relative_path、source_volume_id、file_id（取得可能なら）、size_bytes、allocated_bytes、mtime_utc、attributes、reparse_tag、sha256、streams、metadata、read_status、observed_at_utc。
- **AssetRecord**: asset_id、components（role・FileRecord参照・元名）、capture_date_raw、capture_offset、date_source、date_confidence、association_status、version、aliases。
- **MigrationAction**: action_id、asset_id、source_records、destination_relative_paths、operation（Copy/Reuse/Retain）、required_bytes、reason、plan_sha256。
- **Receipt**: action_id、source hashes/stat、各destの読戻しhash、媒体識別、commit状態、実行コード版、開始/終了UTC、errors、rollback mapping。
- **CleanupDecision**: source_record、F receipt、独立コピーの証跡、構成要素完全性、再検証時刻、Eligible/Retain/Blockedと理由。
- **RunSummary**: SnapshotId、Listed/Copied/Reused/Retained/Pending/Error、論理/占有/空き容量、各工程の時間、完全性の対象範囲。

ファイル行・資産行・別名行の数を混同しない。ファイル数が重複排除で減る場合も、すべての元ファイルに復元先があることを突き合わせる。キャッシュは通常実行の加速にだけ使い、初回受入・削除直前の証明は新しい読取ハッシュで行う。

削除予定のコピーを、別の削除予定のコピーを守る独立証拠に使わない。cleanup全体の依存関係を検査し、全削除後にも各構成要素についてF原本と独立コピーが残ることを確認する。クラウド証拠は取得元、原本/派生版の区別、リモート項目の対応、取得時刻、全成分のhashを含む。C上の同期キャッシュだけをクラウドの独立証拠にしない。

台帳はC側のNTFSに一次チェックポイントを置き、完了した証跡をFにも保存する。F側の画像と台帳を同じ物理ディスク上の「2コピー」と数えない。途中のJSONL末尾や壊れたindexからは検証済みの行だけを復旧し、未完了行を成功へ昇格しない。古い状態ファイルのバージョンは別に保持し、新状態へ黙って流用しない。

## 6. コピーと容量の契約

1. 絶対パス・ルート境界・媒体ID・マーカーを確認する。F文字が別ディスクを指していたら止める。
2. 旧日次タスクを実装時に一時停止し、稼働していないことと同じ名前付きmutexの取得を確認する。iCloud自体は止めない。
3. 安定した入力台帳を取得する。読取前後のサイズ・時刻・file_idとハッシュを記録し、変化したファイルは再列挙して計画を作り直す。
4. 適用対象の全構成要素をSHA-256で読む。候補抽出に名前・サイズを使っても、同一性証明には使わない。
5. F上のstagingへCreateNewで書く。Flush(true)、close、読戻し、source/dest照合を終えてから公開パスへ確定する。
6. 全構成要素の完成と証跡保存後に、その資産をCommittedにする。exFATで電源断に対する完全なトランザクション性があるとは仮定しない。
7. 既存保存へReuseする場合も実ファイルを読み直す。どの原本をどこに復元できるかの別名情報を追加する。
8. 確定済みファイルを上書きしない。異なる内容は別バージョン、未完了ファイルは部分結果として保持・再検証する。

初回はコピーを基本とし、`OLD_F` の一括改名・移動で空きを作らない。容量が不足したら既存コピーを消して進めず、分割計画または別媒体を必要条件として報告する。

```text
必要占有増分 =
  Σ 新規ファイル ceil(size_bytes / 131072) * 131072
  + 新規ディレクトリーの保守的な割当量
  + 台帳・一時コピーの上限
  + 32 GiBの空き予約
```

同じ媒体上の旧データをコピー先と新保存の二つに保持する期間のピークを計算する。約69.49 GiBの候補は照合前には必要量から引かない。「約50 GiBだけ追加」「119 GiB必ず解放」は予測としても確定値にしない。F空き64 GiB未満は警告、32 GiB未満になるバッチは開始しない。Cはダウンロード中も32 GiBを予約する。

実データのパイロットは最大256ファイルまたは2 GiBまでとし、必要な形式・構成要素を一束ごと選ぶ。大きな動画は別途一件だけ試す。実測から全体見積りを更新し、媒体・CPU・ネットワークの計測を分ける。ハッシュ並列数は初期1、最大2とする。

## 7. クラウド取得と日次運用

- 元データの削除・編集をFへ反映しない。変化は別バージョンを追加する。
- メタデータのみのプレースホルダーを完成した保存と数えない。必要な原本を1ファイルずつ取得し、サイズと取得完了状態を確認してからハッシュとコピーを行う。
- 1ファイル取得は600秒上限、同一実行中の自動再試行は最大1回。停止・ログアウト・通信不良はPendingとして残す。成功と混ぜない。
- 新着・更新はsnapshot後の再列挙で差分として処理する。繰り返し更新されるファイルを無限に追いかけず、次回へ保留する。
- F未接続はSkip。媒体が異なる場合はBlocked。Cへ代替保存して無言で使用量を増やさない。
- タスクの毎日20時、ユーザー権限、非表示起動、StartWhenAvailable、同時実行抑止を維持する。新しいCodex定期タスクは作らない。
- 初期移行と日次処理は同じコピー・照合・台帳契約を使用する。日次は存在する保存の通常キャッシュを使い、変更分を読む。
- Windowsの投影だけでLive Photo動画・未編集原本・編集版まで取得できるかをパイロットで確認する。不足はPendingIncompleteAsset。必要ならApple公式の未編集原本のダウンロード経路から別snapshotとして補完する。認証操作は本人が行う。
- Windows上の取得済みファイルは、形式変換された派生版の可能性も保存来歴に残す。未編集原本だと未検証のまま断定しない。
- 日次の入力はICLOUDだけとし、OLD_C/OLD_Fの初回入力を毎日再取り込みしない。F側で手動追加・移動されたファイルは別のローカル変更として台帳に照合し、由来不明のファイルを削除しない。
- 初回と30日ごとに全保存ファイルの読取ハッシュを検証する。月次検査は既存の日次処理内で有効化し、未検証の間はcleanupを禁止する。破損を原本削除へつなげない。
- 状態ファイルとログは世代管理し、状態は3世代、詳細ログは90日。失敗とcleanupの証跡は保持する。写真データの保持期限は設けない。

## 8. C: の解放条件と復元

### 8.1 普通の保存コピー

削除候補は以下のすべてを満たす個別ファイル・完成束に限る。

- 最新の元ファイルとF実体の全SHA-256一致。
- 関連ファイル、編集の差分、名前と復元対応が保全済み。
- Fと異なる物理媒体の読戻しhash、またはクラウドの未編集原本を独立に取得し直したhashが一致。プレースホルダーの存在、同名、緑チェックだけでは証明しない。
- キャッシュに依存しない再検証と復元テストが合格。
- 旧タスクが停止し、新タスクの手動2回・定時1回の受入に合格。
- ゼロ件の未説明の元ファイル、未解決の読取エラー、または対象に関する未説明の資産欠落。

条件を満たすファイルを同じC媒体上の私有retained領域へ個別移動し、7日間保持する。この段階では容量を解放済みと報告しない。保持後の最終検証に合格した許可済みリストだけを、LiteralPathの個別削除で処理する。時間経過だけで削除許可にはしない。日次ジョブは通常ファイルの最終削除を実行せず、独立したcleanupコマンドで実施する。

独立コピーが証明できない分は、C側を第2コピーとして保持する。配置替えと容量解放の進捗を分け、残った容量と理由を明示する。

新F保存へ取り込んだOLD_Fの旧コピーも、F実体のFresh照合とC等の独立コピー、復元合格、7日保持が証明できたものだけ個別に整理する。F上の新旧2フォルダーを独立コピーと数えない。OLD_Fのみに存在した資産は、独立コピーが用意できるまで旧コピーも保護する。初回容量予算には、この旧Fコピーの保持期間を含める。

### 8.2 iCloudの受け取りキャッシュ

クラウドファイルを通常のDelete/Remove-Itemで消さない。F実体の検証、取得済みの構成要素確認、同期済み状態とプロバイダー方針を確認して、Windowsの「空き領域を増やす」に相当するローカル実体の解放を行う。

Microsoftの直接dehydrate APIがプロバイダー方針で許されない場合、無理に呼び出さない。公式のunpinによる非同期解放または本人のエクスプローラー操作を使う。同期ルート・ファイル名の存在は保持し、解放後の再取得とF照合が成功することを少数で試してから範囲を増やす。失敗してもF原本を消さず、キャッシュを残す。

### 8.3 復元・切戻し

- タスク、JS起動器、entry、module、旧状態の完全な私有コピーとSHA-256を保存する。
- 新タスクを停止してmutexを取得し、旧コード・旧状態・タスクXMLを復元し、元のC保存先で小範囲の動作を確認する。
- 7日保持中のファイルは元の相対位置へ戻す。確定削除後はFまたは独立コピーからCreateNewで復元し、hashを照合する。競合名の元ファイルは上書きしない。
- F未接続・媒体不明・F破損時はcleanupを止める。独立コピーからCへ復旧する。
- 電源断、USB抜去、プロセス強制停止後はCommit証跡と全構成要素を再検証する。部分結果の存在だけで完成へ昇格しない。

自動承認レビューで操作を拒否された場合は、別ツール・別シェル・符号化したコマンドで迂回しない。拒否された操作と理由を記録し、必要な本人操作を明示する。

## 9. 受入検査

| ID | 合格条件 |
|---|---|
| A01 | 有効入力すべての元ファイルがCopy/Reuse/Retainに対応。読取エラーと保留の数が報告と一致 |
| A02 | 新規・Reuse先の全バイト列が元hashと一致。元入力も前後で不変 |
| A03 | Live Photo、AAE、RAW、未知形式、別編集版、同名別内容、別名同内容が無欠落で復元できる |
| A04 | 撮影年月の由来が記録され、日時不明は_undated。JSTを推測で付けない |
| A05 | online-only取得失敗・全原本の未確認を成功と数えない |
| A06 | 同じ計画の再適用は保存ファイルを増やさず、二重ジョブは片方だけ実行 |
| A07 | USB誤接続・切断・容量不足・電源断で、元データと確定済み保存を失わない |
| A08 | 月次hash破損が検出され、該当cleanupは拒否される |
| A09 | コード・状態・タスクの切戻しと代表形式の復元を実際に検証 |
| A10 | C通常コピーの削除は最新hashと独立コピー証明と7日保持を満たす個別リストのみ |
| A11 | iCloud上の写真が削除されず、キャッシュ解放後の再取得も同じ内容 |
| A12 | 手動2回・定時1回の新運用が成功し、旧C保存先への新規書込なし |
| A13 | 公開Gitに個人写真・台帳・実機bindings・写真名・認証情報なし |
| A14 | C/Fの論理・占有・空きの変化を別々に測り、移動量と容量解放を混同しない |
| A15 | 旧Fコピーの整理でも独立コピーが残り、別の削除予定ファイルを互いの保護証拠に使わない |

## 10. 判断済み事項と実行時に解消する条件

採用: F通常フォルダー、既存日次タスクの移植、完全バイト保全、関連ファイル単位の検証、元データ非連動、キャッシュの段階的解放、32 GiB予約、7日保持。

保管継続: 古いMacライブラリ。exFAT上のライブラリをMac写真アプリで現役運用する計画ではない。APFSまたはMac OS拡張の別媒体で開く将来工程は別扱い。

実行時の測定・能力検査で解消する条件: 全件内容照合後の必要占有量、Live Photosと原本取得経路、独立したコピーの範囲、未知の再解析ポイントと代替ストリーム、ExifTool配布物の具体的版とhash。いずれも未確認を成功と仮定しない。条件を満たした資産を先に進め、他は明示して保持する。
