# Bank Salary — 公式求人の公開給与レンジ収集

更新日: 2026-10-31

## 目的と確認済みの希望

Morgan Stanley、Goldman Sachs、JPMorgan Chase のニューヨークの求人を網羅的に確認し、公開給与レンジのデータベースと、後から更新できる収集コードを作る。
利用者がニューヨークを指定した理由は給与レンジの公開であり、地域の厳密な定義にはこだわらない。
2026-10-31 に Bank of America と Citi を対象に追加した（利用者の選択）。Citi の自動収集の許可は利用者が確認・取得する前提。

## この実装の範囲（実装者の判断）

- 初回はニューヨーク州を勤務地に含む全職種・雇用形態を対象にする。主勤務地が別地域でも、NY が選択可能な求人を含める。
- 求人を給与記載の有無で除外しない。給与のない求人、取得できなかった求人、解釈が必要な記載を識別する。
- 複数勤務地の給与は地域別に別レコードとして残す。基本給と賞与・株式報酬・総報酬を混同しない。
- 地域は設定で変更できるようにする。初回から米国全土や過去に終了した求人の復元は行わない。
- ローカル CLI とデータファイルを成果物とし、Web アプリ、外部公開、自動スケジュール設定は含めない。

## 成果物と配置

新規プロジェクト `/home/kazumasa/projects/bank-salary/` に Python CLI、意味のある回帰テスト、日本語 README、`docs/STATUS.md` を置く。
他プロジェクト、ルートの依存関係、既存のユーザー変更は変更しない。
Python 標準ライブラリを基本とし、新しい本番依存を追加しない。

実データは gitignored の `/home/kazumasa/projects/_data/bank-salary/` に保存する。
SQLite データベース、求人一覧 CSV、給与レンジ CSV、収集件数・欠損・制限を示す機械可読な検証結果を作る。
CSV は UTF-8 BOM 付きとし、Excel で開ける形式にする。

## 公式のデータ源と取得方針

### Morgan Stanley

- 公式 Eightfold の求人からリンクされている `ms.wd5.myworkdayjobs.com/External` を主要な採用原本とする。
- 公開検索の州フィルターを発見し、ページ送りして一覧を取得後、全求人詳細を読む。
- Eightfold の公開検索と必要に応じて照合し、転載遅延や件数の違いを明記する。公開検索どうしの差を隠して全世界の全件取得とは表現しない。
- 2026-10-31 の事前確認では Workday の NY 州フィルターは 348 件。確定値は実際の本収集の取得日時とともに記録する。

### Goldman Sachs

- `hdpc.fa.us2.oraclecloud.com` の公式 Oracle 採用システムを利用する。
- 公開サイトのメタデータで有効なサイト番号を解決する。URL の別名 `LateralHiring` / `CampusHiring` を API のサイト番号として代用しない。
- 確認済みの有効サイトは `CX_3002`（Lateral）、`CX_3001`（Campus）。両方をページ送りし、同じ求人 ID は重複排除する。
- `higher.gs.com` は事前調査時に HTTP 502。ここだけの独自求人の有無は未確認であり、Oracle サイト内の取得完了と GS の全経路の網羅を区別する。

### JPMorgan Chase

- `jpmc.fa.oraclecloud.com` の公開 Oracle 採用システムを利用する。
- 主要な全社サイト `CX_1001` を中心にする。Chase / Alumni の有効な公開サイトにも一覧を照合し、追加求人があれば含める。
- 公式の NY 州の場所 ID を使い、複数勤務地の求人も取得する。
- `requisitionFlexFields` の `Base Pay/Salary` を優先し、地域別の記載を保持する。

### Bank of America

- 公式キャリアサイトの求人一覧（`careers.bankofamerica.com/services/jobssearchservlet`、`search=getAllJobs`）を全件ページ送りする。`rows` は件数でなく終了位置として扱われる（`start=100&rows=200` で101–200件目）。`state` 引数では絞り込めないため、`stateAbbriviation` と州略号付きの勤務地文字列（`locationString`・`additionalLocations`）で NY を含む求人を選ぶ。
- 詳細は robots.txt が許可する Workday `ghr.wd1.myworkdayjobs.com` の `Lateral-US` を求人番号で検索し、`bulletFields[0]` が完全一致する1件だけを読む。Workday の勤務地は州のない都市名で、対象判定に使わない。
- 公開部門には一覧の LOB（`lob`）、職務カテゴリには `family` を使う。給与は `Pay Transparency details` の勤務地ごとの `Pay range … annualized salary / hourly pay` を地域別に保持する。
- 学生向け採用は別システム（tal.net）で、対象外とする。

### Citi

- `citi.wd5.myworkdayjobs.com` と `jobs.citi.com/search-jobs/` は robots.txt が禁止しているので使わない。
- `jobs.citi.com` の NY 州の勤務地ページ（`/location/new-york-jobs/287/6252001-5128638/3/{page}`、1ページ15件、`data-total-results` で総数を照合）を列挙し、各求人ページの JSON-LD（JobPosting）を読む。
- 公開部門は本文の `Job Family Group`、職務カテゴリは `Job Family`。給与は主勤務地の `Primary Location Full Time Salary Range` だけで、期間の記載がないため `unspecified` とし、地域は主勤務地にする。
- Citigroup の利用規約はデータのスクレイピングを含む無許可の利用を禁じている。収集は利用者が許可を確認・取得する前提で、robots.txt の許可範囲に限り、同じホストへの間隔を1秒以上にする。範囲を広げる場合は先に利用者に確認する。

全社とも検索エンジンや求人転載サイトの件数は母集団の証拠にしない。ログイン、応募、個人情報、非公開 API は扱わない。
HTTP エラー、レート制限、変更されたスキーマでは回数を制限して再試行し、解決しなければエラーを残す。認証やアクセス制限の回避はしない。

## データモデル

- `runs`: 取得開始・終了、対象設定、ソース別の期待件数／一覧のユニーク件数／詳細成功件数／エラー、完了状態。
- `jobs`: 会社と採用システムの求人 ID、初回・最終確認、最新の正常取得内容への参照。
- `observations`: 求人の内容ハッシュ、観測日時、タイトル、部署、原文の職位、勤務地、雇用形態、掲載日、公式 URL、求人本文、原本の圧縮データ。
- `salary_ranges`: 観測への外部キー、下限・上限、通貨、年／時などの単位、給与種別、適用地域、根拠となる原文、解析状態。
- 各 run と実際に観測した求人を関連付け、変更がない場合でもその回で再確認できたことを区別する。

会社間で同じ職位名を同一の職責とはみなさない。職位は原文を残し、必要な場合だけルールによる簡易分類を明示する。
一つの求人で異なる勤務地別レンジがある場合、最小と最大をつないだ架空のレンジを作らない。
年俸と時給は分離し、時給の年換算や賞与の推測は初期実装で行わない。
原文が給与の期間を明記していない場合は `unspecified` として保持する。特に JPM の `Base Pay/Salary` は年／時の単位がないことがあり、金額の大きさだけで確定しない。

## 更新と障害時の動作

CLI で初回取得、更新、CSV 再出力、検証を実行できる。
データベースに観測履歴を蓄積し、同じ内容の原本はハッシュで再利用する。
ページ送り件数の不一致、途中の失敗、詳細の未取得は run を不完全とする。
不完全な取得や対象設定の変更で、過去の求人を募集終了として更新しない。
初期実装では「取得対象で今回確認できた／今回の完全な一覧には存在しない／未確認」を区別し、実際の採用終了日を推測しない。

## 検証と完了条件

1. 各公式サイトの検索結果件数と取得したユニーク求人 ID 数を照合する。更新中の増減や重複による差は再確認し、未解消なら不完全として残す。
2. 全対象求人の詳細を取得し、失敗件数・給与未記載件数・解析保留件数を会社別に数える。
3. 給与抽出を原文と照合し、複数勤務地、時給、固定額、範囲、欠損、誤検出しやすい数値をテストする。
4. 一意性、外部キー、下限 <= 上限、通貨と単位の扱い、再実行時の重複防止、不完全な更新での誤った終了判定を検証する。
5. SQLite と CSV の件数・金額を照合し、会社ごとのサンプルを公式求人と照らす。
6. 初回データ、更新コード、実行手順、未検証の網羅性を引き渡す。「3社すべての公式経路を完全取得」とは、証拠なしに主張しない。

## 容量・運用

概算は約 2,000 求人 × 圧縮前 30 KB = 約 60 MB。SQLite と CSV を含め 200 MB 未満、逐次保存でメモリ 300 MB 未満を目安にする。
大量の HTML ファイルや再試行ごとの原本ディレクトリは作らない。終了時に `du -sh` の実測値を記録する。
接続の同時実行数とリクエスト間隔は控えめにし、再試行回数・タイムアウトを制限する。
