## 計画の具体化

1. **ExifToolの起動方式**: 配布ZIPを検証できなかったため実行せず、作者ソース13.59をコミット固定して既存Windows Git Perlで起動する。ソース・起動器を照合し、Gitの更新などで起動器が変われば保留する。
2. **2波に分割**: 全件案の保守的な必要容量197,817,925,632 Bは空き177,046,814,720 Bを超える。第1波はOLD_C/OLD_Fの32,252件を対象に13,651保存単位、5件保護継続。必要量175,059,238,912 Bには32 GiB予約と一時保存を含む。残るクラウド投影は元位置で保持し、条件を満たした旧Fコピーの整理などで容量を確保してから取り込む。
3. **証跡の割当量**: exFATの128 KiB割当単位を踏まえ、資産ごとの小ファイル大量生成を避けて実行単位のJSONLに保存する。途中行は成功へ昇格しない。末尾だけの途中行は元記録を保全し、確定済みの実体をFresh照合して再開する。途中行や構文上成立する異常記録は自動で無視しない。
4. **関連判定の再確認**: 独立レビューで、識別子がない画像とAAEを別々に分類する問題を確認した。共通名・識別子を候補の束にし、付随情報やメタデータ不足がある画像側も保護する。第1波の旧判定はバイト保存にのみ使用し、削除の証明にはしない。旧判定の記録は`LegacyAssociationNeedsRevalidation`として保持し、整理前に新しい判定へ更新する。

## 独立レビューの修正

配備前レビューで重要度を確認し、1回の修正工程で以下を扱った。原本コピーを止める理由となる破壊経路は見つからなかった。

- 移動・最終削除の直前に代替ストリームを新しく検査する。列挙不能も保護する。
- 読み取り専用への変更も保護し、最終削除で`-Force`を使わない。
- AAE/XMP/RAWや欠落メタデータの関連候補を画像側ごと保護する。
- 判定の版と結果を元位置ごとに保持する。新しいiCloud別名の判定で旧C/旧Fを昇格させない。整理の計画後・保持中に新しい付随ファイルが現れた場合も止める。
- 複数の記録ファイルの読み込み順で別名が欠落しないよう、保存先の整合性を検査し、元位置を単調に統合する。
- F不在時は、C等の独立コピーと媒体・Fresh hashを検証して復元する。制御ファイルの切戻しもFの存在を要求しない。
- 末尾の記録途中を保全して再開し、最終削除後の再実行と削除直後の中断を記録で識別する。

関連判定を厳しくするため保留数は増える。バイト保存と全原本・編集関係の完全性を分けて報告する。
