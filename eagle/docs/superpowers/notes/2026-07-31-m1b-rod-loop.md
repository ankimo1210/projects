## 1. The defect in the shipped scale

`scenarios/p66-padload.toml` carries two comment blocks fifteen lines
apart that contradict each other.

Lines 252-259 derive the whole P66 cluster from a global premise:

> velocities in this file are at 2^10 m/cs (VIGN literal, DDUM denominator
> comment) […] `TAUROD = vel/acc -> fraction = tau_cs / 2^14` (b=14,
> CENTISECONDS)

Lines 265-274 — added **later**, from the spike-B live read-back, and the
only entry in `padload::P66_BSCALE_TABLE` marked `Verified` by
measurement — pin the two words that actually appear in TAUROD's divide:

> VDGVERT and HDOTDISP are DP b=7 in m/cs: HDOTDISP read back as
> `hi=0o36` = 491520 pulses while N63 R2 displayed +00756 (75.6 ft/s), and
> `491520 · 2^-21 m/cs` = 0.2344 m/cs = 76.9 ft/s

The rope's force law divides *those two words*, not `VBRFG`/`VIGN`
(`vendor/virtualagc/Luminary099/LUNAR_LANDING_GUIDANCE_EQUATIONS.agc:1041-1044`):

```
:1041  STODL  HCALC1
:1042           HDOTDISP
:1042  BDSU   DDV
:1043           VDGVERT
:1044           TAUROD
```

**TAUROD was never re-derived after the spike-B measurement landed.** The
b=14 word is 150 cs = 1.5 s only if the numerator is at b=10; at the
measured b=7 it is not. That much is certain regardless of what the right
answer turns out to be.

## 2. What the right scale is — NOT resolved

`b_TAUROD = b_vel - b_acc`, and `b_vel = 7` is measured. The acceleration
side is not pinned, because the path from TAUROD's quotient to a quantity
of known scale passes through two unresolved shifts, each worth exactly
one power of two:

- **`BDDV` by `22D`** (`:1051-1058`). `22D` is a direction cosine built by
  `DOT` of a `CDU*NBSM`-transformed `UNITX` with `14D`. The interpreter's
  `DOT` carries an inherent factor of two for unit vectors — note the
  explicit `SL1` immediately after the `DOT` at `:928` — so whether
  `/AFC/` and the pre-`BDDV` sum share a scale depends on a convention not
  established here.
- **`SR2`** on the gravity path (`:1047`), between `DDV GSCALE` and the
  `DAD` that adds the two terms at `:1050`.

Candidate answers and what the shipped 150 cs word decodes to:

| true b | AGC reads | factor vs intended 1.5 s |
|---|---|---|
| 11 | 0.1875 s | 8× too fast |
| 12 | 0.375 s | 4× too fast |
| 14 (shipped) | 1.5 s | correct |

Either error is a bang-bang oscillator against the rope's own 0.2 s engine
lag (`THROTLAG`, `CONTROLLED_CONSTANTS.agc:134`), which is the observed
symptom. **The direction of the error is certain; the factor is not.**

Anchors that *are* solid and should not be re-derived:

- `MASS` b=16 kg — `ERASABLE_ASSIGNMENTS.agc:1698`,
  "`# (1) MASS AFTER STAGING, SCALE AT B16 KG`".
- `GSCALE` = `2DEC 100 B-11` (`:1477`) — 100 cs at b=11, a DP time in
  centiseconds in the same velocity÷time→acceleration role.
- `/AFC/` at b=-4 m/cs² — `THROTTLE_CONTROL_ROUTINES.agc:206`,
  "MASSMULT SCALES ACCELERATION, ARRIVING IN A AND L IN UNITS OF
  2(-4) M/CS/CS"; `ABRFG` annotated `B+04`.

The gap is only *where in the chain* the b=-4 quantity sits relative to
TAUROD's quotient.

## 3. Why the existing traces cannot settle it

Two methods were tried against `build/traces/telem-m1-run{4,5,6}.jsonl`.
Both failed, and the failures are informative enough to record so nobody
repeats them.

### 3a. Differencing the throttle command against HDOTDISP

`rod_fit`'s original method. `VDGVERT` is not telemetered, but differencing
across a display repaint cancels it *and* the gravity term, leaving
`Δ(a_cmd·cosθ) = -(1/τ)·ΔHDOTDISP`.

Measured:

```
telem-m1-run4.jsonl: tau = 27.0425 s  (slope -0.0370 1/s, r2 0.153, n 36,  75 unsaturated repaints)
telem-m1-run5.jsonl: tau = 27.8745 s  (slope -0.0359 1/s, r2 0.047, n 107, 198 unsaturated repaints)
telem-m1-run6.jsonl: tau = 35.4682 s  (slope -0.0282 1/s, r2 0.040, n 101, 188 unsaturated repaints)
```

r² of 0.15 / 0.05 / 0.04 — **no fit.** The plan's kill criterion (r² ≥ 0.5)
was written before the numbers were seen, and it fired.

**Cause:** the method needs `VDGVERT` constant across each difference, and
`scenarios/pdi-descent.toml` drives a ROD *schedule* (run 4's
`[[245,-5.3],[50,-0.3],[12,0.7]]`). The sim is clicking `VDGVERT`
throughout the entire P66 window, so the cancellation never happens. A
direct look at run 4's repaint samples confirms it: between TIG+992.6 and
TIG+999.6 the command rises 4.2 → 31.0 kN while `HDOTDISP` also rises
−8.11 → −6.10 m/s, which the law forbids at constant `VDGVERT` — the error
term would be shrinking, not growing.

### 3b. Reading MINFORCE off the command floor — DISCARDED

The command floor looked like a `MINFORCE` clamp at half its loaded value:
run 4 bottoms at 178 bits = 2231 N against a pad-loaded 4560 N, and
`4560/2 = 2280 N = 182 bits` sits between run 4's minimum (178) and its 1st
percentile (187). That would have pinned the force words, and with
`b_force = b_MASS + b_acc` it would have pinned TAUROD without resolving
either shift above.

**It is not a clamp.** Histogramming run 4's low tail shows a smooth
distribution — about 10 frames (one guidance cycle at 10 Hz telemetry) at
each of ~40 consecutive bit values, 178 through 259, with no spike
anywhere:

```
  178 bits =  2230.7 N   10
  183 bits =  2293.3 N   10
  187 bits =  2343.5 N   10
  ...                    ...
  255 bits =  3195.6 N   21
  258 bits =  3233.2 N   20
```

A clamp produces a mode; this is a controller sweeping through a range.
Independently, `throttle_cmd_pulses` is our accumulation of the DINC
stream, and the rope's `PIFPSET` drive-past bookkeeping
(`THROTTLE_CONTROL_ROUTINES.agc:99-119`) offsets it from `FC`, so its
absolute level cannot measure a force word in any case.

**What the same data does establish:** runs 4 and 6 hit exactly 4096 bits
= `FEXTRA` (`THROTTLE_CONTROL_ROUTINES.agc:226`, `BIT13`, "4096 PULSES"),
the rope's own full-throttle drive-past constant. Landing on it exactly
validates the bit→newton mapping and the telemetry chain end to end.

## 4. What was built to settle it

- **`runtime/apps/eagle-runtime/src/bin/rod_fit.rs`** (`4c55466d`,
  extended `3eaed239`) — offline estimator, 5 tests.
- **`rod_clicks_cum` in the telemetry wire** (`24d81e56`) — the sim issues
  every ROD click, so it reports the running total and the analysis
  reconstructs `VDGVERT` exactly, at the live-verified 1 ft/s per click.
  Additive field; `SCHEMA_VERSION` stays 2. The handover's selection click
  is issued by `headless.rs`, not `phase8_rod`, and is booked from the
  same latch that triggers it.
- **Click-aware level regression** (`3eaed239`) — with
  `VDGVERT(t) = VDGVERT₀ + k·Δclicks`, the law is a straight line in the
  fully-observed regressor `x = k·Δclicks − HDOTDISP`, so `τ = 1/slope`
  and no constant-`VDGVERT` segment is needed. Recovers τ at 0.1875 /
  0.375 / 1.5 s to within 0.01 s *through* a `VDGVERT` change, so the
  candidate scales are separable.
- **`EAGLE_TELEM_OUT` / `EAGLE_ATT_DEBUG` fail loudly** (`259f6af2`) —
  both did `File::create(p).ok()`. The runtime's cwd is `runtime/` (the
  Makefile does `cd runtime && cargo run`), so the natural
  `EAGLE_TELEM_OUT=build/traces/x.jsonl` from the repo root resolves under
  `runtime/` to a directory that does not exist, and the instrumentation
  silently did nothing. **This cost a full 20-minute descent on
  2026-07-31** before it was noticed. Use absolute paths.

```
  click change ->   0 at t=1204.6s (alt 39.7)
```

**Two consequences, and the second is worse than the first.**

1. The display is dead, so `agc_hdot_ms` is unusable and neither fitting

2. **If a `rod_load` was swallowed, its clicks never reached RODCOUNT** —
   so `rod_clicks_cum` would report clicks the AGC never applied, and
   `VDGVERT` would not be where the count says. That breaks the click-aware
   fit's core assumption independently of the display. Flight 7 also
   counted **41 PROG lamp frames** after ignition, against 0 on runs 4
   and 6, which is consistent with something having gone wrong in the
   dialog — but the code is unknown for the same reason as ledger item 2:
   nothing reads FAILREG after ENGINE ON.

flew carried only `rod_fit` (a separate bin), the `rod_clicks_cum` counter
(`sim.rs` `tick`, a pure accumulator), and the env-var panics (startup
only) — none touches `rod_load`, the script pump, or the DSKY. Run 4's
0.49 repaints/s against runs 5 and 6's ~1.0 suggests the same failure
partially present earlier and never noticed.

**Next flight must capture `--trace-out`.** Run 7 did not, so the KEY REL
and OPR ERR lamp states — which would confirm or refute the swallow
directly — are not recoverable from it. That is the single cheapest thing
that would settle it.

Ranked, and none of it costs a flight to attempt:

1. **Verify the ROD load landed.** `rod_load` writes RODCOUNT and returns

|---|---|---|

The third looks like it worked. It did not. Sweeping the assumed command
lag shows r² is a **periodic function of the lag**, peaking and collapsing
on a fixed cycle:

```
 lag_s     tau_s      r2
   0.0    61.459   0.003
   2.0     6.434   0.297
   4.0     4.422   0.634
   5.0     4.396   0.641   <- peak
   6.0     4.818   0.534
   8.0     8.136   0.188
  10.0    65.859   0.003   <- collapse
  14.0       nan   0.184   <- rising again
```

The limit-cycle period, from `vz` zero crossings, is **19.4 s** — a
quarter period of **4.9 s**. The r² peak sits at **5.0 s**. A
quarter-period shift is exactly what maximizes the correlation between an
oscillation and the response driving it, and the collapse at 10 s is the
half-period anti-correlation. **The regression is measuring the limit
cycle's own geometry, not the control law**, and its "τ" tracks the period
rather than the gain — which is also why τ shrank monotonically as the
assumed lag grew.

**The root cause is structural: a saturated relay limit cycle carries
almost no information about the linear gain inside it.** The loop spends
its time at the stops, crosses the linear band quickly, and every signal
is dominated by phase. All three failures — §3a, the r²=0.04 level fit,
and this one — are the same fact seen three ways.

## 7. What will actually work: an open-loop step test

Stop trying to identify the loop from a descent. Do to `TAUROD` what
spike B did to `RODSCALE`: a short, controlled, live calibration.

`tests/live_spike_p66.rs` already boots to P66 at a benign state and reads
`cmd_pulses` (`:152`). The experiment:

1. Reach P66 and let the rate settle somewhere well inside the throttle
   band — no saturation at either stop.
2. Step `VDGVERT` by a known number of clicks (`rod_load`, now verified to
   land, at a live-confirmed 1 ft/s each).
3. Measure the resulting **step** in commanded thrust before the vehicle's
   own rate responds.

Then `τ = Δ(rate error) / Δ(a_cmd)` directly, from a step whose input is
exactly known and whose output is a single algebraic difference. One clean
step separates 0.1875 / 0.375 / 1.5 s by a factor of 4 to 8; no regression,
no phase, no saturation.

This costs roughly 10 minutes rather than a 20-minute descent, and it is
the same pattern this repo already trusts for `RODSCALE` — which is the
one b-scale in `P66_BSCALE_TABLE` marked `Verified` by measurement.

## 7a. Step test, attempt 1 — the machinery works, the testbed does not

Built as `runtime/apps/eagle-runtime/tests/live_rod_step.rs` (`dfe81515`)
on the spike-B hover choreography. Run 2026-07-31, 418 s:

```
[step] P66 working point: cmd 295 bits (range 262..1243 over 10 s), vz -47.067 m/s, alt 2121.2 m
[step] clicks -1  cmd 295 -> 347 bits (+52)  vz -47.067 -> -68.465 m/s  mass 15133 kg
[step]   dVDGVERT -0.3048 m/s, dHDOT -21.3982 m/s, d(a_cmd) +0.0431 m/s^2  => TAUROD = 489.8426 s
panicked: the AGC refused the step's ROD load (EntryStatus { key_rel: false, opr_err: true })
```

**Two results, one good and one bad.**

**Good: the rejection detection fired, for the first time ever.** The
second ROD load was refused with `opr_err`, and the test stopped instead
of quietly computing a number from a step that never happened. Before
`a984c46a` this run would have produced a plausible-looking τ from a
`VDGVERT` that never moved. That is precisely the failure mode the
detection was added for, and it caught it on its first live outing.

**Bad: the spike-B hover is not a benign testbed, and the premise behind
choosing it was wrong.** At P66 entry the vehicle is at 2121 m falling at
**−47 m/s**, and over the 5 s step window it accelerates to −68 m/s. The
command sits at 295 bits — at the idle stop — and swings 262..1243 over
the preceding 10 s, so it is neither trimmed nor settled.

The measurement is therefore meaningless: `dHDOT` (−21.4 m/s) swamps
`dVDGVERT` (−0.30 m/s) by **70×**, and τ = 490 s is that ratio, not a time
constant. Free fall is inherent to the choreography — P63 parks the
throttle at the DPS idle stop (4560 N) for the whole ZOOMTIME trim phase
against a 15 195 kg vehicle's 24 616 N weight, i.e. −1.32 m/s² for ~30 s
before P66 can take over. The "benign hover at 3000 m" in the test's
header was an assumption, never checked.

**The deeper problem this exposes: the step must dominate the transient,
and no closed-loop state in this project provides that.** τ is recoverable
only when |ΔVDGVERT| ≫ |ΔHDOT|. In the hover spike the vehicle is in free
fall; in the PDI descent P66 limit-cycles from the moment it takes over —
*because* τ is 4-8× too small. Waiting for a quiescent window is circular:
the loop is not quiescent precisely because of the defect being measured.

## 7b. The fix: freeze the plant, not the loop

Make the test genuinely **open-loop**, which attempt 1 claimed to be and
was not. Hold the vehicle's specific force at exactly lunar g so the AGC's
own altitude rate is constant by construction — then `ΔHDOT ≡ 0` and

```text
  TAUROD = dVDGVERT / d(a_cmd)
```

exactly, with no transient to dominate and no dependence on nav-vs-truth
agreement.

The piece already exists: `SyntheticHover::spawn` is the v1 feeder, "a
constant specific force of +1.62 m/s² along SM +X (lunar-surface hover)"
(`runner.rs`), used from boot until ignition. What is missing is a mode
that feeds that constant hover stream **while still tracking the AGC's
`cmd_pulses`** — today `spawn_closed_loop` does the tracking but also
integrates the vehicle, and `spawn` does neither.

That is a small addition to `runner.rs`: a closed-loop variant whose plant
is frozen. With it, one click gives `d(a_cmd) = 0.3048/τ` directly —
1.63 m/s² at b=11, 0.81 at b=12, 0.203 at b=14 — separable by 2× with no
correction term at all.

## 7c. MEASURED: `TAUROD` is b=11 — the AGC reads 0.1875 s

Step test attempt 2, on the frozen plant (`f7296ee5`), 2026-07-31, 380 s.
The freeze held exactly — `vz 0.000 m/s, alt 3000.0 m` for the whole run —
so the AGC integrated a vehicle whose altitude rate never changed.

```
[step] P66 working point: cmd 0 bits (range 0..373 over 10 s), vz 0.000 m/s, alt 3000.0 m
panicked: THRUST DINC loop never moved the actuator off its zero stop
```

**The test failed on a guard, and the guard's own value is the
measurement.** `STARTP66` initialises `VDGVERT` from the current altitude
rate (`LUNAR_LANDING_GUIDANCE_EQUATIONS.agc:157`, `DXCH VDGVERT #
ALTITUDE RATE`), so after the −1 selection click the rate error is exactly
**−0.3048 m/s**, and

```text
  a_cmd = g − 0.3048 / TAUROD
```

with every other term known. At 15 195 kg and g = 1.62 m/s²:

| τ | b | a_cmd (m/s²) | F_cmd (N) | bits |
|---|---|---:|---:|---:|
| 1.5 | 14 (as shipped) | 1.417 | 21 528 | **1718** |
| 0.375 | 12 | 0.807 | 12 265 | **979** |
| 0.1875 | 11 | −0.006 | −85 | **zero stop** |

**Observed: 0 bits.** The command drove all the way to its zero stop,
which requires

```text
  g − 0.3048/τ ≤ 0   ⇒   τ ≤ 0.3048/1.62 = 0.1881 s
```

and b=11 predicts **0.1875 s** — a **0.3 %** match. The weaker bound, taking
the pad-loaded `MINFORCE` (4560 N) as the clamp instead of zero, is
τ ≤ 0.2309 s, which still excludes both other candidates.

**What this does and does not establish.** The measurement is one-sided:
it bounds τ from above and cannot by itself exclude a scale *smaller* than
b=11. It is the derivation that bounds the candidate set from below —
`b_TAUROD = 7 − b_acc` with `b_acc` either −4 (the rope's own
`THROTTLE_CONTROL_ROUTINES.agc:206`) or −5 (if the `BDDV` by the
`DOT`-built cosine shifts one power of two), giving 11 or 12 and nothing
else. **The derivation narrows it to {11, 12}; the measurement excludes 12.
Together they pin b = 11.**

That is also the first independent confirmation that this project's model
of the P66 force law is right at all: three regressions had failed to
show the law describing the data, and here a first-principles prediction
of the commanded throttle came out on the nose.

**Consequence.** `scenarios/p66-padload.toml` ships `TAUROD` at b=14, so
the AGC decodes the intended 150 cs as **18.75 cs = 0.1875 s** — an **8×
too-fast rate loop** against the rope's own 0.2 s `THROTLAG`. That is the
limit cycle.

## 9f. CORRECTION to §9c — most of the "velocity error" is measurement artifact

§9c claimed "a combined ~3.5 m/s velocity error (−3.2 m/s downrange,
−1.3 m/s radial) appears at/near the MM64 transition." **That overstates
what the data supports, and the mechanism was wrong.** Reading the rope's
own definition of the signal is what corrected it.

**`HDOTDISP` is an extrapolation, not a state.**
`LUNAR_LANDING_GUIDANCE_EQUATIONS.agc:1015-1032`:

```
        PIPTIME
    STORE 30D        # TIME IN CS SINCE PIPTIME
    DDV   PDVL
        4SEC(28)
        GDT/2        # <- GRAVITY increment only
    VSU   VXSC
        VBIAS
    VSL2  VAD
        V
    STOVL 24D        # UPDATED VELOCITY
        R
    UNIT
    DOT   SL1
        24D
    STODL HDOTDISP
```

So `HDOTDISP = UNIT(R) · [V + (GDT/2 − VBIAS)·(t − PIPTIME)/4s]` — the
state velocity extrapolated from the last PIPA read **using gravity
alone**. It structurally omits the thrust accrued since `PIPTIME`, so the
displayed rate lags the true rate by the vehicle's own vertical
acceleration, and the lag's SIGN follows the sign of `dvz/dt`.

**That is exactly the "onset" §9c reported.** `dvz/dt` is negative through
P63 (the vehicle is still accelerating downward) and turns positive at the
P63→P64 transition (P64 starts arresting the descent). The error does not
switch on at MM64 — **it changes sign there**, because the quantity it
lags does.

Fitting `err_hdot = −(dvz/dt)·lag + bias` over t = 400–1000 s
(6000 samples):

```
  implied lag = 2.602 s      (2 s guidance period + ~1 s display repaint)
  bias        = -0.329 m/s
  r2          = 0.50
```

A 2.6 s effective staleness is exactly what the mechanism predicts, and it
accounts for about half the variance.

**What survives, and what does not:**

- **The −1.3 m/s radial "velocity error" does not survive** as a
  navigation defect. It is mostly the stale-display term.
- **The −3.2 m/s downrange figure does not survive either.** It rested on
  `RGU` decoding that the validated Rust decoder could **not** reproduce
  (best r = 0.54 across all candidate offsets, §9d). It should not be
  quoted until `RGU` is pinned.
- **The −190 m altitude error survives and is still unexplained.**
  Display staleness cannot produce it: at t = 960 the vehicle is doing
  −7 m/s, so 2.6 s of lag is 18 m against a measured −146 m.
- **The residual bias is suggestive.** −0.329 m/s sustained from ignition
  (t = 344) to P66 entry (t = 988) integrates to −212 m against the
  measured −184.5 m — the right order. But r² = 0.50 with only two
  regimes of `dvz/dt` leaves slope and intercept partly degenerate, so
  this is a lead, not a result.

**Excluded by measurement, not argument:** the AGC's lunar μ.
`CONTROLLED_CONSTANTS.agc:326` gives `MUM = 4.9027780 E8` in m³/cs²
(B-30), i.e. 4.9027780e12 m³/s², against `MU_MOON = 4.9028e12` — a

## 9k. Flight 12 aborted — `--dump-time=1` breaks the boot

```
  2: V01N01 read of 02027 failed 3 times
```

yaAGC's core dump is a synchronous ~18 KB write inside its main loop
(`agc_engine_init.c:441-471` called from `SimManageCoreDump`), and at 1 s

the system.** Passive observation — the watcher copying a file yaAGC was

passive, and the boot choreography is the most timing-sensitive thing in
the run.

**Consequence for 9j's plan.** Per-pass capture via a shorter dump
interval is off the table unless it can be enabled *after* ignition, which

implemented) the AGC-clock-to-wall fit tightens the window from ~100 ms
to ~10 ms, cutting per-sample noise from +-35 pulses to +-3.5; at 104
samples that is a standard error near 5e-4 — at the threshold rather than
5x above it. Marginal, but it costs one ordinary flight with no changes
to yaAGC's behaviour.

## 11. Item 4 cannot close in a crewless P66 — and item 2 may be item 4's fix

means writing a guidance law of our own and calling it a crew.

**The rope already contains the right answer, and we are skipping it.**
P65 is the automatic landing phase, and its law is a **vector** one:

    ACG = (V2FG - VGU) / TAUVERT

(`LUNAR_LANDING_GUIDANCE_EQUATIONS.agc:911-922`, `P65VERT`: `VLOAD VSU /
V2FG / VGU / V/SC TAUVERT`). All three components are driven to the target
velocity. P66's law, fifteen lines below, is the scalar ROD one this
project has spent two sessions on — vertical only. **Nulling horizontal
velocity is structurally P65's job, and P66 cannot do it.** That is not an
inference from flight data; it is what the two routines compute. The scenario hands over at 250 m
specifically to jump over P65, because "this rope's P65 entry is where the
run dies (PROG alarm ...)" (`pdi-descent.toml:47-48`). That alarm is
ledger item 2 and **its code has never been read**.

**The hypothesis this raises: item 2 is a symptom of the bypassed radar.**
Every flight that met the P65 alarm flew with `lrbypass = true`. P65 is
the phase that most depends on the landing radar. If P65's entry alarm is
a radar-data complaint, then M3 — which is what this session has been
building — closes item 2, which unblocks P65, which nulls v_horiz, which
closes item 4. That is one fix for three open items, and it needs no crew
model and no threshold relaxation.

**It is a hypothesis, not a result.** It could equally be unrelated. What
makes it testable now and not before: `bin/agc_state` prints `FAILREG`
(three SP alarm-code registers, `ERASABLE_ASSIGNMENTS.agc:442`) out of the
periodic core dump, so the code can be read passively — no RSET, which
would clear it.

**Decision rule, fixed before the data:** once a flight reaches P64 with
the radar live, raise the handover gate out of the way (or remove it) and
let the rope enter P65. Then:
- No alarm, and P65 flies → item 2 was the radar; measure v_horiz at
  contact and re-run Task 3's gate against it.
- Alarm again → read `FAILREG` from the dump. The code names the
  complaint, which is more than any flight so far has produced, and item 2
  stops being "unknown" whatever the answer.

### Defect 9: the LR pad-load block was never loaded, and nothing declares the altitude scale

`SERVICER.agc:1136-1142`:

```
        CS      FLGWRD12        # TEST LR ALTITUDE SCALE FACTOR
        MASK    ALTSCBIT
        EXTEND
        BZF     +3              # BRANCH IF HIGH SCALE
        CA      SKALSKAL        # RESCALE IF LOW SCALE
        TC      SHORTMP
```

Two facts settle it:

1. **`SKALSKAL` is a pad load and we never load it.**
   `ERASABLE_ASSIGNMENTS.agc:813` — "LR ALT SCALE FACTOR RATIO: .2 NOM".
   `scenarios/p66-padload.toml:22-24` omits the whole LR block on the
   stated premise that "landing radar stays silent in Spike A (no LR
   data-good discretes), P65 is out of scope". **That premise stopped
   being true the moment M3 started driving the radar.** Also missing:
   `RADSKAL` (the Doppler bias, `SERVICER.agc:1134`), `DELQFIX` (the
   reasonableness test's tolerance), `V2FG` and `TAUVERT` (which are
   P65's *entire* guidance law — see §11).

2. **Nothing in the rope ever writes `ALTSCBIT`.** It is bit 9 of
   `FLGWRD12` = `RADMODES` (`FLAGWORD_ASSIGNMENTS.agc:1110-1112`), and
   `SERVICER.agc:1137` is its *only* reference in Luminary099. Checked
   Luminary131 and Luminary210: same — one read, no write. It is
   **external state the LR supplies**, and in this architecture the only
   thing that can supply it is our sim, which does not.

Fresh start zeroes the flagwords, so bit 9 is clear ⇒ **low scale** ⇒ the
AGC multiplies the reading by `SKALSKAL`, which is **zero**. The computed
slant range collapses, `DELTAH = 0 − HCALC`, and the AGC drives its own
altitude toward zero on every update. That is the ±3 km oscillation.

### The counter cannot represent the braking phase, either

`HSCAL` is 1.079 ft/bit (`CONTROLLED_CONSTANTS.agc:168`) = 0.3288792
m/count, and `RNRAD` is a 15-bit counter (±16383). So the largest
altitude the high scale can express is **5388 m** — and the low scale,
at ×0.2, only 1078 m. Flight 18 was asking it to carry 15 213 m
(46 257 counts). Even with the scale declared, altitude data-good must
not be asserted above the counter's range; this is not a workaround but
what the real LR's range gate does.

### Next actions, in order

1. **Declare high scale.** Set `FLGWRD12` bit 9 before the LR is first
   read. A blunt pad-load write would clobber live radar bits — the same
   hazard `p66-padload.toml:27-28` already documents for `FLAGWRD8` — so
   use the choreography's read-modify-write path, not a manifest word.
   High scale is the right choice: it needs no `SKALSKAL` at all, so it
   removes a multiply-by-zero instead of adding an unpinned b-scale.
2. **Gate `LR_RANGE_DATA_GOOD` on the counter's range** (|count| ≤ 16383,
   i.e. altitude ≤ 5388 m). Above that, assert velocity-good only.
3. **Load the rest of the LR block** — `RADSKAL`, `DELQFIX`, and (for
   §11's P65 experiment) `V2FG` and `TAUVERT`. Each needs its b-scale
   derived and cited before it is written, and `SKALSKAL` is only needed
   if step 1 is ever reversed.
4. Then re-fly with `lrbypass = false`.

`lrbypass` is back to `true` in `scenarios/pdi-descent.toml`: with the
scale undeclared the radar makes navigation worse than bypassing it, and
the acceptance scenario should sit in its best known state between
experiments.

### 13a. ch13 bit 7 is a red herring — but the velocity read is FIVE SAMPLES

Bit 7 resolved, cheaply and negatively: `INITREAD` clears the select with
`CS ALLREAD / WAND CHAN13  # REMOVE ALL RADAR BITS` where `ALLREAD` is
`OCT 17` (`P20-P25.agc:2739, 2785-2792`). The radar bits are 1-4 only.
Bit 7 belongs to some other ch13 function, and `decode_ch13` is right to
ignore it.

**The real finding is in the same table** (`P20-P25.agc:2738-2760`):

```
LRALT           TC      INITREAD -1     # ONE SAMPLE PER READING.
ALLREAD         OCT     17
LRVELZ          TC      INITREAD        # <- no -1
                OCT     16
...
# LRVEL IS THE ENTRY TO THE LR VELOCITY READ ROUTINE WHEN 5 SAMPLES ARE
# WANTED.  ENTER WITH C(A)= 0,2,4 FOR LRVELZ,LRVELY,LRVELX RESP.
LRVEL           TS      TIMEHOLD
                CAF     FIVE            # SPECIFY FIVE SAMPLES
```

**LR velocity is a five-sample read; altitude and both RR quantities are
one-sample reads.** The rope accumulates into `SAMPLSUM`
(`P20-P25.agc:2798-2801`), and `RADSKAL`'s own comment is "SCALE TO RADAR
COUNTS **X 5**" (`SERVICER.agc:1134`) — the sum of five is what the
scaling expects.

`phase6b_landing_radar` drives `RNRAD` **once per ch13 rising edge**. If
the rope runs five sample gates per velocity reading, our responder
satisfies the first and leaves the counter holding a stale value for the
other four, so `SAMPLSUM` accumulates five copies of one sample instead
of five independent ones. That is a velocity error which is *silent while
the rope ignores LR velocity* and bites the moment it starts using it —
which is the TIG+360 s signature exactly.

This is the next thing to fix, and it is ahead of the "velocity off,
altitude only" bisection in §13, because it predicts that bisection's
result rather than merely measuring it. Read `INITREAD`/`LRVEL` fully
first: the open question is whether the five gates are five ch13 activity
cycles (which our rising-edge responder would already see) or five reads
inside one activity window (which it would not).

### 13b. The five samples are five activity cycles — the theory is WEAKENED, not confirmed

`P20-P25.agc:2899-2909`:

```
NOEND           TS      NSAMP
RESAMPLE        CCS     SAMPLIM         # SEE IF ANY MORE TRIES SHOULD BE MADE.
                TCF     +2
                TCF     DATAFAIL        # N SAMPLES NOT AVAILABLE.
                CAF     BIT4            # RESET ACTIVITY BIT.
                EXTEND
                WOR     CHAN13          # RESET ACTIVITY BIT
                TC      RESUME
```

**Each sample is its own ch13 activity cycle.** The read clears bit 4
(`P20-P25.agc:2873`) and `RESAMPLE` re-sets it for the next one, then
RESUMEs to wait for the next RADARUPT. So `phase6b_landing_radar`'s
rising-edge responder sees all five edges and recomputes from current
state each time — which is what a real LR would give. §13a's mechanism
does not hold as stated. Recorded so it is not re-derived.

**What §13a's reading DID surface, still unverified: the sign
convention.** `P20-P25.agc:2879-2885`, immediately after the velocity
select resolves:

```
                CAF     POSMAX
                MASK    RNRAD           # magnitude, 14 bits (POSMAX = 37777)
                AD      LVELBIAS
                TS      L
                CAE     RNRAD
                DOUBLE
                MASK    BIT1            # the sign bit, extracted separately
                DXCH    ITEMP3
```

The rope builds a **double-precision** reading whose high half is
`|RNRAD| + LVELBIAS` and whose low half is `RNRAD`'s sign bit recovered
through `DOUBLE / MASK BIT1`. `eagle_sensors::lr::vel_raw_counts` returns
a single signed count and the responder drives the counter with PINC /
MINC to reach it; **nothing in this project has ever checked that the
counter's sign, as the rope reconstructs it here, is the sign we
intend.** A sign error here is invisible while the rope ignores LR
velocity and appears the moment it uses it — which remains the TIG+360 s
signature.

Next: hand-decode this sequence for a known count (both signs), assert it
in `lr.rs` against `vel_raw_counts`, and only then fly. The bisection
(velocity off, altitude only) stays as the fallback if the decode is
clean.

### 13c. The sign convention decodes CLEAN — inside the gated window

Hand-decoded, no flight needed. `DOUBLE` is `AD A`, and in 15-bit one's
complement doubling a negative word produces the end-around carry that
sets bit 1; doubling a positive one does not. So `CAE RNRAD / DOUBLE /
MASK BIT1` is exactly **"is RNRAD negative"**, and the high half is
`(RNRAD & POSMAX) + LVELBIAS` — magnitude only, 14 bits.

For the counts this project actually sends, that is correct:
`vel_raw_counts` returns `trunc(v/q) - LVELBIAS`, which the §13 window
gate now confines to `[0, 16383]`. RNRAD is therefore never negative on a
velocity read, the sign flag is always 0, and
`(RNRAD & POSMAX) + LVELBIAS` recovers `trunc(v/q)` exactly. **The sign
lead is dead**, and the window gate is what kills it — one of flight 19's
two "correct but not the bug" fixes turns out to close a different hole.

the fallback: **LR velocity data-good OFF entirely, altitude only.** If

chain is sound; if it does not, it is in neither and the search moves to
what the rope does with the reading (`SERVICER`'s reasonableness test and
`PSTHIBIT`, which is skipped before HIGATE).

## 16. Flights 24-26 — the socket is not a hardware pulse line

The first X target in Run 22 was about 14,341 counts away from the prior
word. The old responder emitted one PINC/MINC packet per count, while yaAGC's
default socket service accepts one packet per 51 AGC instructions. Tens of
thousands of packets cannot complete inside a 90 ms radar gate. `VMEAS`
therefore contained a partially delivered word even though every conversion,
sign and beam vector was individually correct.

Run 24 temporarily primed `RNRAD` to the velocity bias and ran yaAGC with
`--interlace=0`. This diagnostic passed both trajectory comparisons, proving
the throughput mechanism:

| TIG+ | Run 24 - Run 11: alt / vz / vh / tilt |
|---:|---:|
| 360 | +19.2 m / +0.06 m/s / +0.85 m/s / -0.75 degrees |
| 420 | +22.7 m / -0.29 m/s / +1.03 m/s / -0.66 degrees |

It was not retained: accelerated interlace reduced the AGC clock rate and the
large altitude transition later raised PROG alarm `01210` at TIG+469.6.
Correcting the range word to the positive hardware magnitude, as NASSP's LGC
interface does, gave complete five-sample transactions but still exposed the
same delivery limit later: Run 25 raised `00520` at +474.6. Presenting range
and velocity DATA GOOD as standing discretes in Run 26 moved that alarm only
to +482.4. Those flights separated data semantics from transport but were not
solutions.

yaAGC already exposes the hardware-shaped answer: counter command 5 is
SHINC and 6 is SHANC. Fourteen SHINCs discard any previous 14-bit word;
fourteen SHINC/SHANC commands then load the new bits most-significant first.
Every `RNRAD` value is therefore replaced exactly in **28 packets**,
independent of its delta. Unit tests start from arbitrary prior words and
replay the same shift operations to prove the exact final value. The
`--interlace=0` workaround and runner-side `RNRAD` priming were removed.
