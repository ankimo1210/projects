# 研究成果物の重複整理（2026-10-11）

## 対象と原因

RB-F04 動的モデル横断ヘッジの旧検証成果物を対象に、内容と参照パスを維持して
同一バイトのファイルを共有する。金融モデル、数値、研究の受入条件は変更しない。
GiB は (2^{30}) バイト、容量はファイルの割当ブロックを inode ごとに一度数えた値。

肥大の主因はスクリーンショットではなく、旧保存形式の配列とメタデータだった。
同じ配列が入力・キャッシュ・risk・rollout から繰り返し保存され、配列の別名参照も
個別に展開されていた。JSON にも大きな参照構造が繰り返し入っていた。
1ファイルの上限は、検証全体の容量上限にはならない。

測定時、旧検証フォルダは約115 GiB、新しい保存形式を検証中のフォルダは約23 GiB。
通常の main の `johnhull/` は約2.1 GiBだった。これらは別作業ツリーの測定値であり、
Git に新たに138 GiBをコミットしたという意味ではない。

## 整理方法

[共有スクリプト](../scripts/share_closed_artifacts.py)は標準ライブラリのみを使う。
対象は公開後に書き換えない、ディレクトリ構成も変わらない静止した成果物ツリー。
稼働中の新しい pilot の出力先、Git 履歴、C:/F: の独立した保管庫は対象外。

- `rb-f04-array-receipt-v1` の canonical JSON と自己ハッシュを検査する。
- `metadata.json` と `arrays.npz` の実バイトを双方でSHA-256照合する。
  NPZ の展開サイズも receipt と照合し、配列はメモリへ展開しない。
- 同一ファイルシステム・所有者・権限・サイズの一致を要求する。
  既定で直近1時間のファイルと1 MiB未満のファイルを除外する。
- 元 inode の一時 backup を持ち、hardlink を原子的に置換して再照合する。
  journal とディレクトリを fsync し、通常の失敗・割込みでは元 inode を復元する。
  復元の永続化失敗は backup を保持して停止する。
- 検証後の backup 削除に続く障害も停止し、確定を確認できない件数を記録する。
  外部 hardlink が残っている inode の解放量は0とする。
- receipt のバイトとパスは変更しない。共有されたファイルの mtime は共有元の値になる。
  元の mtime は journal に残す。ctime と inode は保存形式の管理情報として変わる。

共有後のファイルに追記・上書きすると他の参照先にも影響する。
新しい計算は新しい成果物フォルダへ保存し、公開済みファイルを in-place 更新しない。
この共有は同じディスク上の容量整理であり、独立したバックアップの代わりにはならない。

## 再実行

WSL のリポジトリ root から実行する。`ROOT` は静止した旧成果物フォルダ、
`JOURNAL_DIR` は既に存在する、対象の外側にある同一ファイルシステムのフォルダ。
journal のファイル名は実行ごとに新しくし、私有ログを Git に追加しない。

```bash
# 監査だけ。推計容量は実際の解放量と区別する。
uv run --no-sync --package hullkit python johnhull/scripts/share_closed_artifacts.py \
  --root "$ROOT" --journal "$JOURNAL_DIR/audit-new.jsonl"

# 同一バイトを照合した上で共有。金融計算の負荷を抑えて実行する。
nice -n 19 ionice -c 2 -n 7 \
  uv run --no-sync --package hullkit python johnhull/scripts/share_closed_artifacts.py \
  --root "$ROOT" --journal "$JOURNAL_DIR/apply-new.jsonl" --apply \
  --max-read-gib 256 --max-seconds 900 --max-links 30000
```

読み出し量・実行時間・置換試行数の上限は管理作業を止めるためのもの。
上限終了は研究の成功を意味しない。再監査して残った候補だけを処理する。
異常停止時は journal と保持された backup を確認し、原因が不明のまま再実行しない。

## 実施結果

整理前の旧対象は127,496ファイル、121,503 inode、123,529,728,000バイト。
最も新しいファイルも約22時間前で、新しい pilot は別フォルダへ出力していた。
監査の重複候補は15,913 inode、23,166,283,776バイト（約21.6 GiB）。

適用は約13分で正常終了。15,913ファイルを共有し、23,166,283,776バイト
（21.575 GiB）を実際に解放した。旧対象は100,363,444,224バイト（93.471 GiB）になった。
候補の推計と解放量は一致し、処理後の再監査では対象条件を満たす重複候補は0件。

別の確認処理で、127,496ファイルのパスとサイズ・権限、41,136件の receipt のバイト、
共有した全15,913ファイルの参照先とSHA-256を再照合してPASS。
共有後の1,722 inode、4,903,286,778バイトを完全にハッシュし、同じ inode の参照先を全件確認した。
変更対象以外の inode と mtime は不変。ファイル割当量の減少も journal と完全一致した。

除外は6件。単独のRED/GREEN判定記録には対象の配列・metadataがなく、
意図的な改竄テストの receipt は正規のJSONではないため、これらは元のまま保持した。
適用中の復元・未確定commitは0件。私有 inventory・操作journal・独立照合結果は
旧作業ツリーの `.superpowers/storage-cleanup-20261011/` に保存し、Git には追加しない。

旧研究ブランチのHEADは整理前後で不変。進行中の金融workerも整理後に稼働を確認した。
現行workerが旧フォルダの入力を読む経路はあるが、そこへの書込みは行わず、出力先は別のまま。

Windows C: の回収には別途オフライン縮小が必要で、WSL を停止するため本作業では実施しない。
